# Legacy background jobs

Redis is explicitly enabled by `REDIS_URL`, `REDIS_HOST`, or `REDIS_PORT` in the backend process environment or its loaded `.env`. `REDIS_URL` takes precedence. Host/port configuration also accepts `REDIS_PASSWORD` and `REDIS_DB`; omitted host/port values default to `127.0.0.1:6379` only after Redis is explicitly configured. The QA launcher must pass `QA_REDIS_PORT` as backend `REDIS_PORT`.

Without any Redis setting, no Bull queue or query worker is registered. Authenticated history remains available, and creating a new authorized job returns HTTP 503 without persisting or queueing it. Cancelling a queued job persists cancellation even if the queue is unavailable or Bull holds an active-job lock; workers check cancellation before and after execution.

Jobs store a server-authored actor ID, personal user ID, and request authentication epoch in existing JSON metadata. Client metadata cannot override these values or the admitted SQL/source. Workers read the persisted request rather than trusting queue SQL. Admission, execution, result reads, and cancellation require the current active actor, unchanged epoch, and current source ownership plus read permission. An old job without the server-authored actor snapshot fails closed; it must be resubmitted explicitly under a current session. There is no automatic upgrade of old epochs and no schema migration.

These checks protect the legacy unrestricted SQL boundary. They do not change Studio or enterprise consumer permissions. Revocation prevents result publication/access after SQL, but does not interrupt a database query already in flight. Live Redis/MySQL execution is an integration check performed by the main worker.

The main-worker smoke driver is `node scripts/qa-main-legacy.cjs /absolute/runtime.json`; append `--no-redis` for a separate fresh runtime with Redis entirely unconfigured. Both modes require the owned MySQL/API gate from `qa-enterprise-access-matrix`, an empty user table with next ID 1, and backend `LEGACY_OPERATIONS_USER_IDS=1`. Redis mode requires the owned backend's loopback `REDIS_URL`. The driver never builds or starts services and must be run by main after the final runtime is ready.

Evidence is written under the Git-ignored `.aiwf/evidence/TC050-main-legacy/<run>/`. Only `fixture.private.json` contains fixture credentials, with mode 0600; the containing directory is mode 0700. Fixtures remain available for Ego. An execution window that finishes too early fails the smoke; progress 30 observes the active worker stage and does not independently prove entry into native SQL. Redis endpoint selection is checked against the owned backend environment, while separate Redis-container custody remains a main-owned precondition.

## Shared-table collision separation

Background and dormant queue results previously both mapped to `job_results`, while the two active telemetry models both mapped to `analytics_events`. Global entity discovery combined their incompatible required columns and foreign keys, even without activating the queue module. The models now use `background_job_results`, `queued_job_results`, `analytics_collected_events`, and `client_analytics_events`. The old two tables are deliberately unmapped and retained, including all their old columns and rows; neither entity is mapped back onto them. This does not activate the dormant queue module.

`SeparateLegacyEventAndJobTables1792620300000` in `src/migrations/1792620300000-separate-legacy-event-and-job-tables.ts` creates the four tables additively. Main registers it explicitly in `AppModule`. Existing environments require a separately approved migration run before serving the new model mappings; a fresh development `synchronize` run is not evidence that historical migration was applied. No running runtime was migrated by this worker.

The backfill keeps source IDs, available timestamps, and text payloads. Job rows copy only when exactly one family link exists, it names a current matching parent, there is no duplicate parent link in the old table, and required destination fields are present and non-null. Telemetry rows from a mixed schema require exclusive family-specific values; common fields alone do not establish provenance. Client events also require a real session parent. Invalid JSON, lossy numeric conversions, oversized fields, incomplete required history, and ambiguous or orphan rows remain solely in the unchanged legacy tables for manual review. Existing destination IDs are never overwritten, and reruns do not duplicate copies. JSON columns retain their logical JSON content; database JSON storage can canonicalize formatting.

This is a conservative valid-row backfill, not a claim that all historical events/results are available through current APIs. Remaining legacy rows need a separate provenance and access review before any manual migration. Rollback refuses to drop data. The local real SQLite persistence and preservation tests cover both entity families and repeated migration; actual MySQL child-schema verification and fresh HTTP/Redis execution remain Main/Galileo checks.

The smoke driver now sends both public telemetry POSTs and verifies their stored rows in the separate tables, including client decimal values. HTTP 204 alone is insufficient because both ingestion services deliberately swallow insert errors. Its cancellation/revocation result checks query `background_job_results`. No telemetry endpoint or permission contract was changed by this table separation.
