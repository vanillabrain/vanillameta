# VanillaMeta 검증

## 프로젝트와 범위

현재 cwd/워크트리가 VanillaMeta인지 package.json, AGENTS.md, git status로 확인한다. 다른 프로젝트에는 적용하지 않는다. 이 스킬은 기능 구현·배포·외부 알림 권한을 추가하지 않는다.

저장소의 `docs/testing/workflow.md`를 읽어 실행 단계와 변경 범위를 선택한다. 대상 UI 케이스만 `docs/testing/cases.md`에서 읽는다. 설치 경로를 저장소 경로로 추정하지 말고 현재 워크트리에서 문서를 찾는다. 연결된 문서가 없으면 설치 워크트리의 문서를 몰래 대신 적용하지 말고 누락을 보고하고 현재 프로젝트 지침에서 확인 가능한 범위만 진행한다.

## 부담을 줄이는 선택

- 파일 저장/작성 중 전체 테스트·빌드·E2E를 실행하지 않는다. 사용자가 요청한 범위가 우선이다.
- 의미 있는 변경 뒤 관련 단위/API를 실행한다. 기능 완료에는 필요한 타입/린트/빌드와 변경 UI 확인을 추가한다.
- 통합에는 빠른 전체 단위 검사와 영향받는 핵심 E2E, 출시에는 전체 핵심 E2E와 변경된 MD 화면 검증을 선택한다.
- CSS/문구만 바뀌면 해당 Aside 화면 확인(대응하는 기능 MD 케이스 전체를 억지로 실행하지 않고 관찰 범위만 보고), SQL/숫자/권한은 하위 정확성 검사, 저장 흐름은 해당 core E2E를 우선한다. 인증/공통 API처럼 영향이 넓거나 불명확하면 범위를 넓힌다.
- 기존 실행의 커밋·작업 diff·환경·픽스처가 관련 변경 없이 같다면 통과 결과를 재사용한다. HEAD가 같다는 것만으로 미커밋 코드 변경을 놓치지 않는다.
- 실패 수정 뒤 해당 검사부터 재실행한다. 전체 검사는 공통 영향/추가 실패/명시적 요구가 있을 때 확대한다.
- 신규 자동 UI 테스트는 반복 회귀 가치가 높은 경우만 만든다. 기존 검증을 활용하고 새로운 범용 프레임워크/매 실행 코드 생성은 피한다.

## 실행

`workflow.md`의 정확한 명령을 사용한다. 기본 Playwright 8개는 직접 실행하거나 파일/grep으로 선택한다. 확장 `qa`는 명시적 위험/시나리오가 있을 때만 실행하며 4개 BE/provider 기동 비용을 고려한다. 기본 suite를 실행했다고 확장 QA가 통과했다고 말하지 않는다.

테스트용 기존 서버를 재사용할 수 있으면 재사용한다. 데이터 초기화가 필요하거나 공유 상태가 적절하지 않으면 격리 명령을 사용한다. 포트 충돌로 다른 세션 서버를 종료하지 않는다. 테스트별로 만든 정확한 자원 ID만 정리한다. 브라우저의 비인증 검증에는 로그인된 사용자 탭을 재사용하지 않는다.

Aside UI는 사용 가능한 `aside-browser` 스킬을 읽고 `aside guide`(직접 조작 시 `aside guide repl`) 지침으로 실행한다. 화면을 snapshot/실제 캡처로 읽고 사용자 이름·역할 기반으로 동작한다. 기존 정상 탭/서버를 확인하고 재사용한다. Aside 사용 불가면 이유를 기록하고 사용자가 허용한 대체 브라우저 검증을 적용하거나 BLOCKED로 남긴다. 브라우저 확인 없이 UI 검증 완료를 선언하지 않는다.

각 MD 케이스의 입력/기대 수치/지속 상태를 유지한다. 재배치된 버튼은 화면에서 다시 찾되, 기능 삭제/동작 실패를 임의 우회하거나 기대값을 바꾸지 않는다. 저장은 재조회/새로고침, 수치는 고정 정답으로 확인한다. 스크린샷만으로 정확성/권한을 판정하지 않는다.

## 증빙과 종료

저장소 밖 실행 폴더에 커밋/diff 기준·URL·환경·픽스처·실행 케이스 ID·결과를 기록한다. 단위 작업의 결과 화면은 PNG로, 여러 단계의 사용자 흐름은 첫 조작부터 결과까지 영상으로 기록한다. 최종 보고에 캡처와 재생 가능한 영상을 연결한다. 미디어 확인·민감정보 처리와 도움말 녹화 방법은 [실행 검증 스킬](../verify-vanillameta/SKILL.md#evidence)을 따른다. 인증 토큰/비밀번호를 결과에 출력하지 않는다.

PASS / FAIL / BLOCKED / NOT_RUN으로 기록한다. 일부 변형만 확인했다면 그 범위를 적는다. 예상과 다른 화면은 최초 실패 증빙을 남기고 재검사 기록을 분리한다. 현재 요청에 필요한 검증이 확인되면 중단하고 임의로 모든 케이스를 추가 실행하지 않는다.

최종 보고는 변경 범위, 실행한 검사와 명세 ID, 결과/증빙, 생략 범위와 이유, 남은 위험을 짧게 적는다. 검사를 위한 검사의 숫자를 늘리지 않는다.

## UI 컴포넌트 디자인·레이아웃 회귀

UI 요소를 추가하거나 변경할 때 구현 전 기준을 잡고, 의미 있는 배치 변경 뒤 실제 화면에서 아래 항목을 확인한다. 기능 완료 시에도 마지막 코드의 화면을 확인한다. 변경 요소뿐 아니라 같은 행·패널의 주변 요소와 부모 컨테이너까지 비교한다. 전체 화면·전체 테스트를 매 저장마다 반복하지 않는다.

- **기준**: 기존 공통 컴포넌트·테마의 크기/간격/타이포그래피를 먼저 사용한다. Rill 참조 화면은 같은 뷰포트·상태에서 배치·밀도·컨트롤을 대조한다. 변경 전 캡처 또는 확인된 기준 화면을 남겨 작업 중 틀어짐을 판별한다.
- **크기·높이·정렬**: 버튼·입력·선택·아이콘의 폭/높이, padding, gap, margin, 라벨/값/아이콘의 기준선과 수직 중앙 정렬을 확인한다. 같은 역할의 컨트롤은 크기와 높이가 일관되어야 하며 텍스트·아이콘이 잘리거나 클릭 영역을 벗어나지 않아야 한다.
- **레이아웃**: 행/열 배치, 컨테이너 폭·여백, flex/grid 줄바꿈, 표의 열 폭·헤더·셀 정렬, 고정 영역, 스크롤과 overflow를 확인한다. 요소 추가로 주변 컨트롤이 밀리거나 겹치거나 불필요한 빈 공간·스크롤이 생겼는지 비교한다.
- **폰트·표현**: font family/size/weight, line-height, 제목·라벨·값·보조 문구의 위계, 숫자/단위 가독성, 색 대비, 테두리·배경·radius와 아이콘 크기의 일관성을 확인한다. 예외 크기는 기존 토큰과 다른 이유가 있어야 한다.
- **상태·폭 변화**: 영향받는 기본/선택/비활성/포커스/로딩/빈 결과/오류 상태와 긴 라벨·큰 수치를 확인한다. 기본 데스크톱과 좁은 지원 뷰포트에서 줄바꿈·높이 변화·잘림·겹침을 점검한다. 전체 반응형 검증을 하지 않았다면 확인한 폭만 보고한다.

Aside 실제 캡처로 눈에 보이는 균형을 확인하고, 애매한 크기·정렬 차이는 해당 요소의 bounding box/computed style을 지원되는 브라우저 도구로 확인한다. DOM snapshot·타입 검사·기능 테스트 통과만으로 디자인 PASS를 선언하지 않는다. 발견한 회귀는 수정 후 같은 뷰포트·상태로 재확인한다. 증빙에 변경 요소, 뷰포트, 상태, 기준 대비 결과와 미확인 항목을 적고 **기능 PASS와 디자인 PASS를 별도로** 기록한다.

## UI 응답성 회귀 방지

렌더러의 모듈 경계, 상태 갱신 순서, 입력 반응에 영향을 주는 변경에 적용한다. 시작, 화면 전환, 스트리밍 중 입력, 대량 목록·차트 갱신 중 변경과 관련된 동작을 고른다.

### 구현과 리뷰

- 브라우저 코드에서 서버 전용 모듈, 파일시스템·DB·Node API를 직접 또는 재수출을 통해 가져오지 않는다. 공유 타입과 직렬화 가능한 계약은 양쪽에서 안전하게 사용할 수 있는 모듈에 둔다. 대량 파싱·집계가 입력을 막으면 기존 API·DuckDB 워커 경로를 검토한다. 대표 측정 흐름은 [VanillaMeta 웹 응답성](../../docs/architecture/web-responsiveness.md)을 따른다.
- 깜빡임·화면 튐·초점 경쟁을 `setTimeout(0)`, `requestAnimationFrame`, `requestIdleCallback`으로 미루기 전에 상태 소유자와 실제 완료 신호를 찾는다. 렌더 완료, 응답 도착, 이전 요청 취소처럼 필요한 조건을 명시적으로 연결한다. 디바운스·애니메이션·유휴 작업처럼 스케줄링 자체가 요구사항이면 목적을 코드로 드러내고, 화면 이탈이나 조건 변경 시 예약 작업을 정리한다.
- 경계를 넘는 import나 같은 타이밍 우회가 재발하면 기존 린트·의존성 검사·CI에 좁은 규칙을 넣거나, 안정된 완료 신호를 제공하는 공용 API와 회귀 테스트를 만든다. 검사에는 허용되는 공유 계약과 차단되는 import를 각각 확인한다. 의도적인 타이머까지 포괄 금지하지 않는다.

### 제품 코드에서 `useEffect` 직접 사용 금지

- 화면·컴포넌트·기능 전용 훅에 `useEffect`를 새로 추가하지 않는다. 이름을 바꾼 import, `React.useEffect`, Effect를 그대로 전달하는 범용 래퍼에도 같은 방침을 적용한다. 기존 호출의 책임을 바꾸는 PR에서는 해당 호출을 대체한다.
- 파생값은 렌더링에서 계산하고, 클릭·입력·제출에 따른 작업은 이벤트 핸들러에서 실행한다. 서버 조회와 캐시는 기존 쿼리 훅에 맡긴다. 외부 저장소 구독이나 브라우저 API 연동은 먼저 기존 공용 훅과 어댑터를 사용한다.
- 직접 호출은 외부 시스템 연동을 맡는 공용 훅·어댑터에 한해 코드 리뷰에서 허용한다. 리뷰에 기존 API로 해결할 수 없는 이유와 동기화 대상, 시작·정리·취소 조건을 남긴다. 해당 경계의 검증에서 재구독, 언마운트, 늦게 도착한 응답 중 관련 경로를 확인한다.
- PR에서 신규 직접 사용과 변경된 기존 호출을 검사한다. 자동화할 때는 새 위반부터 막고, 검토된 어댑터 예외는 파일 단위 허용 목록으로 관리한다. 검사에 직접 import·별칭·네임스페이스 호출 차단과 허용된 어댑터 동작을 포함한다.

### 동작과 속도 검증

- 기능 지도 또는 MD 케이스에서 시작 상태, 클릭·키 입력 순서, 완료 조건을 가져온다. 실행 중인 앱에서 화면·포커스·저장 결과를 확인한다. 깜빡임이나 가상 목록의 화면 튐은 최종 캡처에 놓칠 수 있으므로 빠른 전환, 연속 입력, 응답 역전 등 문제를 드러낸 조작 순서를 재현하고 영상이나 상태 기록으로 확인한다.
- 성능을 조사하거나 개선하려면 작업 전후에 같은 장비, 빌드 모드, 데이터, 뷰포트, 캐시 상태로 여러 번 측정한다. 시작 → 첫 입력 가능, 스트리밍 중 키 입력 → 텍스트 표시, 긴 화면 열기·전환 → 조작 가능처럼 사용자 기준으로 시작점과 끝점을 고정한다. 서버·네트워크 시간과 렌더러 처리 시간이 함께 들어가면 각각 기록한다.
- 원시 표본, 실행 횟수, 중앙값과 느린 표본을 남긴다. 표본이 충분하면 p95를 보고하고, 적으면 개별 표본과 최댓값을 보여 준다. 느린 실행의 CDP Performance 트레이스에서 긴 작업, 렌더·레이아웃, GC를 확인하고 재현된 원인에 맞는 검사만 추가한다. 캡처·트레이스 수집 오버헤드는 비교 측정과 분리한다.
- 결과에는 기능 확인과 성능 측정을 별도로 기록한다. 스크린샷은 화면 상태의 증빙으로 사용한다. 비교 가능한 측정이 없으면 속도 개선 수치를 기재하지 않는다.

## 시각화 디자인·경쟁 UX 비교

대시보드 변경은 숫자 정답 통과와 UI 가시성 통과를 분리한다. Rill과 같은 데이터/질문 비교를 요청받으면 `docs/testing/design-rill-parity.md`의 DESIGN-01~04를 사용한다. 같은 기간·필터·질문·뷰포트, KPI·단위·축·범주 이름·정렬·공간 활용·필터/AI 수정 흐름을 비교하고 새 캡처를 남긴다. LLM 미설정/기능 미구현을 수동 SQL·수동 차트로 대체해 동등성 PASS로 보고하지 않는다. 원본 시간 이동 및 화면 반올림은 별도 기록한다. 접근성·모바일 미실행은 통과가 아니다.


## UI 컴포넌트 추가·수정 시 디자인 회귀 확인

기능 추가와 함께 해당 컴포넌트 및 인접 영역의 시각적 상태를 확인한다. 변경 전 기존 토큰·대표 화면을 기준으로 잡고, 기능 완료 뒤 동일 상태/뷰포트에서 비교한다. 기존 기능 MD 전체를 재실행하지 않고 변경한 요소와 영향을 받는 레이아웃만 확인한다.

- 크기·정렬: 컨테이너 폭/높이, 버튼·입력 높이, 기준선, 수평/수직 정렬, padding/gap/margin, 표의 행 높이와 열 폭을 비교한다. 긴 이름·값에서도 버튼/레이블이 사라지거나 이웃 영역을 밀어내지 않는지 확인한다.
- 글꼴·색상: 제목/본문/보조문구/숫자의 크기·굵기·행간과 계층, 기존 테마의 색·테두리·반경·그림자·대비를 맞춘다. 포커스·활성·비활성·오류 상태도 실제 화면에서 읽힌다.
- 레이아웃: 데스크톱/390px 대표 모바일에서 wrapping, 카드/대화상자/표의 높이, 고정 헤더·푸터 중첩, 가로 넘침을 확인한다. 가로 스크롤은 명시한 표 내부에 한정하고 숫자 정렬·축약값/정확한 값 접근을 유지한다.
- 상태별 확인: 정상·로딩·빈 결과·오류 중 변경에 관련된 상태만 선택한다. 저장/필터/탭 전환 후 크기와 정렬이 틀어지거나 잘린 내용이 없는지 확인한다. 키보드 포커스가 컨트롤/스크롤 내부에서 보이는지도 포함한다.

MD에는 해당 변경의 대표 뷰포트·입력(긴 이름 포함)·기대 배치를 적고, 핵심 전후 캡처와 필요 시 실제 bounding box/overflow 수치를 증빙한다. 숫자/기능 PASS와 디자인 PASS를 분리하며 캡처를 직접 살펴보지 않고 디자인 완료로 판정하지 않는다. 차이 발견 시 해당 UI만 수정·재캡처하고, 미검증 상태·실기기는 NOT_RUN으로 남긴다. 치수를 이유 없이 전역 고정하거나 새 디자인 시스템을 도입하지 않고 기존 프로젝트 토큰/컴포넌트를 우선한다.
