# VanillaMeta 검증

## 프로젝트와 범위

현재 cwd/워크트리가 VanillaMeta인지 package.json, AGENTS.md, git status로 확인한다. 다른 프로젝트에는 적용하지 않는다. 이 스킬은 기능 구현·배포·외부 알림 권한을 추가하지 않는다.

저장소의 `docs/testing/workflow.md`를 읽어 실행 단계와 변경 범위를 선택한다. 대상 UI 케이스만 `docs/testing/cases.md`에서 읽는다. 설치 경로를 저장소 경로로 추정하지 말고 현재 워크트리에서 문서를 찾는다. 연결된 문서가 없으면 설치 워크트리의 문서를 몰래 대신 적용하지 말고 누락을 보고하고 현재 프로젝트 지침에서 확인 가능한 범위만 진행한다.

## 부담을 줄이는 선택

- 파일 저장/작성 중 전체 테스트·빌드·E2E를 실행하지 않는다. 사용자가 요청한 범위가 우선이다.
- 의미 있는 변경 뒤 관련 단위/API를 실행한다. 기능 완료에는 필요한 타입/린트/빌드와 변경 UI 확인을 추가한다.
- 통합에는 빠른 전체 단위 검사와 영향받는 핵심 E2E, 출시에는 전체 핵심 E2E와 변경된 MD 화면 검증을 선택한다.
- CSS/문구만 바뀌면 해당 Aside 화면 확인(대응하는 기능 MD 케이스 전체를 억지로 실행하지 않고 관찰 범위만 보고), SQL/숫자/권한은 하위 정확성 검사, 저장 흐름은 해당 core E2E를 우선한다. 인증/공통 API처럼 영향이 넓거나 불명확하면 범위를 넓힌다.
- 기존 실행의 커밋·작업 diff·환경·픽스처가 관련 변경 없이 같다면 통과 결과를 재사용한다. HEAD가 같다는 것만으로 미커밋 코드 변경을 놓치지 않는다.
- 실패 수정 뒤 해당 검사부터 재실행한다. 전체 검사는 공통 영향/추가 실패/명시적 요구가 있을 때 확대한다.
- 신규 자동 UI 테스트는 반복 회귀 가치가 높은 경우만 만든다. 기존 검증을 활용하고 새로운 범용 프레임워크/매 실행 코드 생성은 피한다.

## 실행

`workflow.md`의 정확한 명령을 사용한다. 기본 Playwright 7개는 직접 실행하거나 파일/grep으로 선택한다. 확장 `qa`는 명시적 위험/시나리오가 있을 때만 실행하며 4개 BE/provider 기동 비용을 고려한다. 기본 suite를 실행했다고 확장 QA가 통과했다고 말하지 않는다.

테스트용 기존 서버를 재사용할 수 있으면 재사용한다. 데이터 초기화가 필요하거나 공유 상태가 적절하지 않으면 격리 명령을 사용한다. 포트 충돌로 다른 세션 서버를 종료하지 않는다. 테스트별로 만든 정확한 자원 ID만 정리한다. 브라우저의 비인증 검증에는 로그인된 사용자 탭을 재사용하지 않는다.

Aside UI는 사용 가능한 `aside-browser` 스킬을 읽고 `aside guide`(직접 조작 시 `aside guide repl`) 지침으로 실행한다. 화면을 snapshot/실제 캡처로 읽고 사용자 이름·역할 기반으로 동작한다. 기존 정상 탭/서버를 확인하고 재사용한다. Aside 사용 불가면 이유를 기록하고 사용자가 허용한 대체 브라우저 검증을 적용하거나 BLOCKED로 남긴다. 브라우저 확인 없이 UI 검증 완료를 선언하지 않는다.

각 MD 케이스의 입력/기대 수치/지속 상태를 유지한다. 재배치된 버튼은 화면에서 다시 찾되, 기능 삭제/동작 실패를 임의 우회하거나 기대값을 바꾸지 않는다. 저장은 재조회/새로고침, 수치는 고정 정답으로 확인한다. 스크린샷만으로 정확성/권한을 판정하지 않는다.

## 증빙과 종료

저장소 밖 실행 폴더에 커밋/diff 기준·URL·환경·픽스처·실행 케이스 ID·결과를 기록한다. 핵심 성공 결과와 실패 화면만 캡처하고 채팅에 실제 이미지로 남긴다. 인증 토큰/비밀번호를 결과에 출력하지 않는다.

PASS / FAIL / BLOCKED / NOT_RUN으로 기록한다. 일부 변형만 확인했다면 그 범위를 적는다. 예상과 다른 화면은 최초 실패 증빙을 남기고 재검사 기록을 분리한다. 현재 요청에 필요한 검증이 확인되면 중단하고 임의로 모든 케이스를 추가 실행하지 않는다.

최종 보고는 변경 범위, 실행한 검사와 명세 ID, 결과/증빙, 생략 범위와 이유, 남은 위험을 짧게 적는다. 검사를 위한 검사의 숫자를 늘리지 않는다.

## 시각화 디자인·경쟁 UX 비교

대시보드 변경은 숫자 정답 통과와 UI 가시성 통과를 분리한다. Rill과 같은 데이터/질문 비교를 요청받으면 `docs/testing/design-rill-parity.md`의 DESIGN-01~04를 사용한다. 같은 기간·필터·질문·뷰포트, KPI·단위·축·범주 이름·정렬·공간 활용·필터/AI 수정 흐름을 비교하고 새 캡처를 남긴다. LLM 미설정/기능 미구현을 수동 SQL·수동 차트로 대체해 동등성 PASS로 보고하지 않는다. 원본 시간 이동 및 화면 반올림은 별도 기록한다. 접근성·모바일 미실행은 통과가 아니다.


## UI 컴포넌트 추가·수정 시 디자인 회귀 확인

기능 추가와 함께 해당 컴포넌트 및 인접 영역의 시각적 상태를 확인한다. 변경 전 기존 토큰·대표 화면을 기준으로 잡고, 기능 완료 뒤 동일 상태/뷰포트에서 비교한다. 기존 기능 MD 전체를 재실행하지 않고 변경한 요소와 영향을 받는 레이아웃만 확인한다.

- 크기·정렬: 컨테이너 폭/높이, 버튼·입력 높이, 기준선, 수평/수직 정렬, padding/gap/margin, 표의 행 높이와 열 폭을 비교한다. 긴 이름·값에서도 버튼/레이블이 사라지거나 이웃 영역을 밀어내지 않는지 확인한다.
- 글꼴·색상: 제목/본문/보조문구/숫자의 크기·굵기·행간과 계층, 기존 테마의 색·테두리·반경·그림자·대비를 맞춘다. 포커스·활성·비활성·오류 상태도 실제 화면에서 읽힌다.
- 레이아웃: 데스크톱/390px 대표 모바일에서 wrapping, 카드/대화상자/표의 높이, 고정 헤더·푸터 중첩, 가로 넘침을 확인한다. 가로 스크롤은 명시한 표 내부에 한정하고 숫자 정렬·축약값/정확한 값 접근을 유지한다.
- 상태별 확인: 정상·로딩·빈 결과·오류 중 변경에 관련된 상태만 선택한다. 저장/필터/탭 전환 후 크기와 정렬이 틀어지거나 잘린 내용이 없는지 확인한다. 키보드 포커스가 컨트롤/스크롤 내부에서 보이는지도 포함한다.

MD에는 해당 변경의 대표 뷰포트·입력(긴 이름 포함)·기대 배치를 적고, 핵심 전후 캡처와 필요 시 실제 bounding box/overflow 수치를 증빙한다. 숫자/기능 PASS와 디자인 PASS를 분리하며 캡처를 직접 살펴보지 않고 디자인 완료로 판정하지 않는다. 차이 발견 시 해당 UI만 수정·재캡처하고, 미검증 상태·실기기는 NOT_RUN으로 남긴다. 치수를 이유 없이 전역 고정하거나 새 디자인 시스템을 도입하지 않고 기존 프로젝트 토큰/컴포넌트를 우선한다.
