## 도입 원칙

### 사용자 지정 비교·UI 기준 — 2026-10-14

이후 기능은 항상 실행 중인 Rill 데모와 비교·대조하면서 개발하고 검증한다. UI는 Rill의 화면 구성과 조작 흐름을 가깝게 구현한다. 이 사용자 지정 기준은 기존의 UI 도입 판단보다 우선한다. Nest/React/MUI/ECharts와 서버 DuckDB는 유지하되, 기존 위젯 배치를 유지하는 것 자체를 목표로 삼지 않는다.

- 상단 기간·시간대·비교 컨트롤과 필터 칩, Measure 선택과 KPI/추세, Dimension 순위·상세, Explore/Pivot 전환, 하단 Model Data 흐름을 UI 기준으로 삼는다. 밀도·간격·타이포그래피·선택/로딩/빈 결과/오류 상태도 비교한다. 커머스 용어와 접근성·모바일 대응에 필요한 차이는 이유를 기록한다.
- 기능마다 Rill에서 같은 조작을 먼저 확인하고 우리 화면에서 재현한다. 같은 데이터·지표식·기간·시간대·필터·정렬로 수치와 상호작용을 대조한다. Rill 모델의 날짜 이동 등 변환을 정렬하지 않은 원본 파일 비교를 동등한 조건으로 보고하지 않는다.
- 기간/필터를 KPI→차원 상세→Pivot→원본 행까지 보존하는지 확인한다. 지표 값, NULL/0 처리, 비율/가중 평균, 비교 증감과 총계는 독립 정답 및 API/XHR로 확인한다.
- 같은 뷰포트와 상태의 Rill/VanillaMeta 캡처를 짝으로 남기고, 수치 일치·배치 유사성·상호작용·반응형을 분리 판정한다. 차이와 미실행은 명시한다. 캡처는 저장소 밖 증빙 경로에 보관한다.
- 이미 확인한 Rill 동작은 버전/설정/데이터와 해당 기능에 변화가 없으면 증빙을 재사용한다. 대응 기능이 실제로 연결되기 전에는 UI 모양만으로 기능 완료를 주장하지 않는다.

Rill의 핵심은 데이터→지표 정의→조건을 바꾸는 탐색→다시 열 수 있는 상태의 연결이다. VanillaMeta에서는 커머스 운영자가 SQL 없이 같은 흐름을 사용할 수 있게 한다. 기존 Nest/React/MUI/ECharts, 서버 DuckDB worker, 메타데이터 DB를 유지한다. Rill의 코드 편집 중심 화면이나 Go/Svelte 스택을 옮기는 작업은 필요하지 않다.

운영자가 답해야 하는 질문은 "이번 주 매출이 왜 바뀌었나", "어느 채널/상품에서 환불이 늘었나", "같은 조건으로 내일 다시 볼 수 있나"이다. 기능 우선순위는 이 질문을 해결하는 순서로 정한다. 기간·시간대·집계식·원본 행의 의미가 일치해야 하며, 예쁜 차트만으로 동등성을 주장하지 않는다.

## 1차 구현 계약: KPI 현재/이전 추세 겹쳐 보기

대상은 대시보드 분석의 `BOARD_NUMERIC`이다. 이미 응답에 있는 `trend`, `previousTrend`, 비교 기간을 사용한다. 첫 단계에서 기간 계산/API/저장 스키마를 바꾸지 않는다. 기존 `comparePrevious`를 켰을 때 같은 좌표계에서 두 추세를 읽게 하는 것이 완료 조건이다.

1. 현재는 실선, 이전은 점선으로 표시하고 텍스트 범례를 제공한다. 색만으로 구분하지 않는다. 두 선은 0을 포함하는 같은 Y 범위를 사용한다. 각각 정규화한 두 선을 겹쳐 차이를 왜곡하지 않는다.
2. X 정렬은 서버가 알려준 현재/이전 기간 시작점의 상대 시간으로 한다. 배열 인덱스나 첫 관측점을 기준으로 붙이지 않는다. 예를 들어 현재 둘째 날 관측이 없고 이전 둘째 날 값이 있으면 해당 위치에 이전 값만 표시한다.
3. 첫 단계는 UTC 일별로 한정한다. 주/월의 부분 버킷은 단순 인덱스 정렬로 대응시키지 않고 안내와 기존 개별 표를 유지한다. 달력 대응 규칙은 시간대/달력 비교 단계에서 확정한다.
4. NULL은 선을 끊고 빈 날짜를 0으로 채우지 않는다. 한 점·모두 NULL·음수·다른 값 범위·이전 조회 불가를 처리한다. 비교 불가 사유를 숨기거나 이전 기간을 현재 값으로 대체하지 않는다.
5. 정확한 원래 날짜/값을 제공하는 표를 유지한다. 이전 점의 원본 행 조회는 이전 기간 fingerprint와 원래 timestamp를 사용한다. 현재 날짜 필터로 잘못 조회하지 않는다.
6. 비교 해제·조건 변경·조회 실패에서 이전 선을 잘못 남기지 않는다. 최신 성공 응답/미적용 조건 안내는 기존 정책을 따른다. 390px와 키보드 탐색을 검증한다.

작업 파일은 `frontend-web/src/pages/Dashboard/Components/MetricTrend.tsx`, `trendGeometry.ts`, `DashboardAnalysis.tsx`와 관련 테스트다. 기하 계산 테스트에서는 공통 Y 축, 시작점 기준 정렬, NULL 구간을 독립 예상 좌표로 검증한다. 화면 검증에서는 기존 비교 fixture의 API 값과 정확값 표를 대조하고 현재/이전 원본 조회 payload를 각각 확인한다. 첫 단계 완료 보고에 단위 검사와 실제 화면/XHR를 구분한다.

## 2차 구현 계약: 시간대와 커머스 기간 의미

UTC 기본값으로 기존 저장 보기와 호환하고 `Asia/Seoul` 등 검증된 IANA 선택을 추가한다. 날짜 UI만 KST로 바꾸지 않는다. 선택 지역의 자정→UTC 반개구간, 날짜 필터, 일/주/월 버킷, 상대 기간 재평가, 개인 뷰, Assistant 문맥, 원본 행 조회가 같은 시간대를 사용해야 한다. DST가 있는 지역의 23/25시간 일자를 포함해 검증한다. 잘못된 timezone은 명시적으로 거절한다.

Commerce의 결제/환불 발생일 기반 현금 이벤트와 주문일 기준 코호트는 서로 다른 지표다. 동일한 '매출 비교' 옵션으로 묶지 않는다. 주문 코호트의 이후 환불이 포함되는 기준 시점/스냅샷을 응답과 화면에 명시한다. 먼저 기존 UTC 계산 oracle와 금액 최소단위 정밀도를 유지한 뒤 선택 시간대의 자정 경계 fixture로 확장한다. 전년/달력 비교는 윤일·월 길이·부분 기간 정책을 정한 뒤 별도 케이스로 추가한다.

## 3·4차 구현 경계

차원 변화 순위는 같은 필터·snapshot·집계식으로 두 기간을 계산하고 현재에만/이전에만 존재하는 차원을 포함한다. 이전 0/NULL을 무한 증감률이나 0%로 만들지 않는다. 상위 N을 자른 결과의 브라우저 재정렬은 전체 차원의 변화 순위가 아니므로 혼동하지 않게 표시한다.

개인 뷰 확장은 지표 선택/정렬 UI와 서버·클라이언트 whitelist를 함께 바꾼다. 정렬은 위젯별 대상과 방향을 저장하고 대시보드 revision 검사를 유지한다. 표시용 정렬은 `widget.datas`를 직접 변경하지 않으며 차트의 시간 순서와 원본 조회 대응을 보존한다. 기존 version1 보기의 기본값을 유지한다. Rill의 URL 전체 저장 방식을 그대로 받아들이지 않고 소유권과 엄격한 상태 검사를 유지한다.

## 전체 구현 목표와 실행 단위

목표는 커머스 운영자가 SQL 없이 데이터를 연결하고 동일 조건의 지표를 탐색하여 매출·환불 변화를 확인한 뒤 저장한 분석을 데이터 갱신 후 다시 사용하는 서비스다. 현재 단일 상시 Nest 서버·DuckDB worker·영속 볼륨을 유지한다. 각 단위는 Rill 실제 화면과 조건·결과·UI를 비교하며 [검증 절차](../testing/workflow.md)를 따른다.

| ---------------- | -------------------------------------------------------------------------------------------------------------- |
| 동적 탐색        | 저장 Measure와 Dimension 선택, 검색·다중 값 필터, 기간/시간대/비교가 KPI·추세·순위·원본 페이지에 동일하게 적용 |
| 탐색 확장        | 숫자 범위 필터, 차원 상세/변화 정렬, 정확한 시점·기간별 기여 행, 지역 달력 비교 경계                           |
