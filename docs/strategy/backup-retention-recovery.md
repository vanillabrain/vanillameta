# 최소 백업 보존·별도 보관·키 복구 절차

2026-10-16. 단일 상시 서버 + 영속 FILE_UPLOAD_DIR 파일럿 기준이다. 2026-10-31부터 메타데이터 백업은 PostgreSQL 17 `pg_dump`를 정본으로 한다. 추가 큐/백업 서버/새 라이브러리 없이 DB dump·파일 복사·사전 검사로 시작한다. 아래 주기/기간은 **운영 도입안**이며 스케줄러·외부 저장소·자동 삭제는 설정하지 않았다. 과거 MYSQL03~06은 MySQL 당시의 역사적 선택 검증이며 PostgreSQL 수용 증거가 아니다. PostgreSQL 복원 훈련은 [전환 계획](../plans/postgres-metadata-cutover.md)을 따른다.

## 보존 단위와 도입안

| 항목         | 파일럿 도입안                                                      | 현재 상태                            |
| ------------ | ------------------------------------------------------------------ | ------------------------------------ |
| 정기 세트    | 일1회, 완료된 최근 일별7개·주별4개·월별3개                         | 수동 절차만 정의                     |
| 변경 전 세트 | 마이그레이션/대량 소스 교체 전에 추가 보관, 복원 확인 전 hold 유지 | MYSQL03 사전 백업 복귀만 검증        |
| 별도 보관    | 로컬 복구용1개 + 다른 장애 영역의 암호화된 보관1개                 | 실제 오프사이트 미설정               |
| 키 보관      | 데이터 백업과 별도 비밀 저장소, 백업별 keyRef 기록                 | 독립 저장소 복구 미검증              |
| 복구 연습    | 도입 시/월1회/마이그레이션 뒤 선택 세트로 격리 복구                | MYSQL03~06 로컬 선택 조건만 검증     |
| 목표         | RPO24시간·RTO60분을 파일럿 검토 출발점으로 사용                    | 측정/SLA 아님, 고객 요구로 확정 필요 |

같은 세트를 일/주/월 슬롯에서 참조할 수 있고 중복 실체는 늘리지 않는다. 단순 상한 계산은14개 세트 + 변경 전 hold 세트다. 이번 샘플 한 세트는85,506,242bytes이므로14개가 매번 같은 크기라면 약1.20GB/보관 위치, 두 위치 약2.39GB다. 이는 압축/증가분/보관 버전/비밀 저장 비용을 제외한 샘플 계산이며 운영 용량 예측이 아니다. 실제 파일 크기·증가량·허용 데이터 손실에 맞춰 주기와 예산을 바꾼다.

## 작성·별도 보관·삭제 순서

1. 새 쓰기와 파일 수입을 중지하고 진행 중 요청/워커가 끝난 상태를 확인한다. DB와 파일의 동일 시점은 이 절차로 확보한다. PostgreSQL dump만으로 외부 파일까지 같은 시점을 보장하지 않는다.
2. 새 비공개 세트 디렉터리에 metadata.sql과 FILE_UPLOAD_DIR 전체(활성/보관 버전 포함)를 복사한다. 별도 신뢰 위치에 크기/SHA-256 manifest를 작성하고 `verify-backup.py` 성공을 확인한다. 실패/미완료 세트로 이전 정상 세트를 덮어쓰지 않는다.
3. 세트 바깥의 운영 목록에 backupId/UTC작성시각/앱커밋/DB엔진·버전/마이그레이션 이력/파일 수·크기/manifest SHA-256/keyRef/검증시각/hold/보관기한을 기록한다. keyRef는 비밀 저장소 항목·버전의 식별자이며 키 값이나 키의 해시가 아니다. 해당 목록을 backup 루트 안에 추가하면 MYSQL05의 정확한 파일 목록 검사에서 거절될 수 있으므로 바깥에 둔다.
4. 외부 보관소가 정해지면 전송·보관 암호화와 복구 담당자의 읽기 권한을 확인하고 새 세트 이름으로 업로드한다. 원격 업로드 완료만으로 복구 가능을 판정하지 않는다. 새 임시 위치로 내려받아 별도 manifest와 비교하고 복원 연습을 한다. 키는 같은 버킷/압축 파일/동일 접근 권한 묶음으로 보내지 않는다.
5. 모든 보관 위치의 검증 결과를 기록한 뒤 보존 만료 후보만 검토한다. 마지막 복원 가능한 정상 세트, 변경 전 hold, 아직 필요한 키 버전은 삭제하지 않는다. 보관 만료가 됐어도 새 정상 세트/별도 보관 검증이 실패했으면 삭제를 보류한다. 이번 변경은 실제 파일/키 삭제와 주기 실행을 하지 않는다.

외부 보관소가 없거나 같은 서버/VM의 다른 디렉터리에만 복사한 상태는 오프사이트 완료가 아니다. 실제 서비스 선택·권한/계정·비용 확인과 반출 승인은 도입 단계에 남긴다. 고객 데이터의 지역/보존 요구도 그 단계에서 확정한다.

## 암호화 키를 잃었거나 잘못 설정한 경우

현재 `crypto.util.ts`의 유효 키는 **CONFIG_SECRET_KEY가 있으면 그 값, 없으면 ACCESS_SECRET**이다. 후자는 인증용 비밀과 결합될 수 있는 기존 호환 경로다. 백업 시 실제로 어떤 항목/버전으로 암호화했는지 keyRef에 기록한다. CONFIG_SECRET_KEY를 새로 추가하거나 ACCESS_SECRET을 바꾸면 과거 암호문의 키도 자동 변경되는 것은 아니다.

1. 새 키 생성/기존 암호문 덮어쓰기/자동 재암호화를 하지 않는다. 앱 쓰기를 재개하지 않고, 원본 세트와 복원 DB를 보존한다. 올바른 키 없이 AES-GCM 암호문을 복구할 수 있다고 안내하지 않는다.
2. 해당 백업의 keyRef로 **동일한 원래 유효 키**를 승인된 비밀 저장소에서 복원 담당자에게 제공한다. 채팅/명령 인자/로그/SQL dump/화면 캡처에 값을 남기지 않는다. 환경 설정은 별도 비공개 파일/기존 비밀 주입 경로를 사용한다.
3. 격리 DB와 별도 파일 루트에서 사전 검사→DB 복원→복호화→파일 경로 연결→읽기 전용 집계→저장/게시 영수증 조회를 확인한다. 경로 변경 시 sourceRevision 변경과 명시 재생성이 필요할 수 있다. 암호문이 존재한다는 것과 복호화·조회 성공은 구분한다.
4. 복원 세트의 정답/영수증과 원본 불변을 확인한 뒤 접근 권한과 쓰기 재개를 검토한다. 이전 JWT 인증 상태까지 영속 복구됐다고 가정하지 않는다. 필요한 키 버전은 해당 백업이 보존되는 동안 유지한다. 새 키로의 회전/전체 소스 재암호화는 별도 설계·검증 작업이다.

키가 없거나 틀리면 암호화된 connectionConfig의 복호화는 실패한다. 기존 평문 connectionConfig는 하위 호환으로 키 없이 읽힐 수 있으므로 **키 누락이 모든 앱 요청을 차단하는 시작 검사라고 해석하지 않는다**. SQL dump에 평문 설정/사용자 데이터가 있을 수 있어 전체 백업을 민감 자료로 관리한다. 이번 로컬 검증은 프로세스에서 키를 숨긴 연습이며 실제 키 삭제/독립 비밀 저장소 복구는 수행하지 않았다.

## 종료 기준과 남은 운영 gate

로컬 절차의 종료 기준은 손상 거절, 원래 키로의 정확한 복호화·정답 집계, 원본/복원 DB 불변 및 비밀 미노출이다. 운영 준비 완료에는 별도 위치에서 실제 내려받기/키 회수/복원 연습이 추가로 필요하다. 복구 시간을 다운로드·검사·DB복원·파일/키연결·읽기 확인·서비스 재개 단계로 측정하고 마지막 정상 백업 시각과 장애 시각으로 실제 데이터 손실 구간을 기록한다. 현재 실측 RPO/RTO·호스트 손실·PITR·운영 부하·실제 고객 수용은 미검증이다.
