# 외부 베타 M1 — 사용자 간 데이터 격리 증명

2026-10-24 · Draft / PASS_SELECTED. [계획](../plans/external-beta-launch.md) M1의 "사용자 간 데이터 격리 증명" 단위다. 이 문서는 "격리가 완벽하다"는 선언이 아니라, 아래 시험이 무엇을 확인했고 무엇을 확인하지 못했는지의 기록이다.

## 방법

1. **정적 감사**(코드 읽기): 사용자가 닿는 모든 컨트롤러 경로의 소유권 검사를 표로 만들고 의심 지점을 찾았다.
2. **경로 목록 시험** `backend-api/src/route-inventory.spec.ts`: 운영 모드(`NODE_ENV=prod`)의 앱이 마운트하는 모든 라우트를 읽는다. 정적 모듈, `{ module }` 동적 모듈, forwardRef, **Promise를 돌려주는 비동기 동적 모듈**(백그라운드 작업 모듈)을 모두 따라가고, 알 수 없는 import 형태는 건너뛰지 않고 실패한다. 이 앱에는 전역 인증 가드가 없고(`@AuthPublic`은 아무것도 읽지 않는다) 컨트롤러마다 가드를 붙여야 하므로 새 컨트롤러는 기본이 열림이다. 인증으로 세는 가드는 `JwtAuthGuard`·`LocalAuthGuard`·`LegacyOperationsGuard`를 **클래스 동일성으로** 비교한 것뿐이다. `JwtAuthGuard`를 상속한 다른 가드는 인증으로 세지 않으며, 알려진 `StudioPublicationGuard`는 `GET /studio/publications/:token`에서만 비인증을 허용하므로 그 라우트만 허용 목록에 있다. 허용 목록의 항목이 더는 익명이 아니어도 실패한다.
3. **두 사용자 HTTP 시험** `backend-api/scripts/isolation-probe.mjs`: 실제 이미지·MySQL 스택에서 초대 코드로 사용자 A·B를 만들고, A가 파일을 올려 소스·데이터셋·위젯·대시보드를 만든 뒤 B가 A의 id로 43개 경로를 호출한다. 통과 조건은 모두 충족해야 한다.
   - B의 응답은 403이거나, 존재하지 않는 id도 받는 404여야 한다(그 밖의 400/409/422/401은 소유권 거절로 인정하지 않고 실패).
   - B의 응답은 존재하지 않는 id에 대한 응답과 같아야 한다(다르면 id 존재 신호이므로 실패). 토큰 없는 호출은 401이어야 한다.
   - A가 자기 id로 **안전하게 되풀이할 수 있는 호출**(조회와 읽기성 POST)은 A가 거절(401/403/404)이나 B와 같은 응답을 받으면 실패한다. B의 거절이 "모두를 거절하는 경로"가 아니라 소유권 때문임을 보이기 위해서다. 데이터를 바꾸는 호출(PUT·DELETE·게시·공유·복사)과 AI 호출은 대조가 없다.
   - B의 목록은 200이어야 하고(B의 토큰이 유효하다는 대조) A의 데이터가 없어야 하며, A의 `/database`·`/dataset`·`/widget`·`/dashboard` 목록에는 A의 항목이 보여야 한다.
   - 위젯·대시보드 등 설정 단계가 하나라도 실패하면 해당 경로를 조용히 빼지 않고 실행 자체를 실패시킨다. B의 시도 뒤에 A의 데이터가 그대로여야 한다.
   - 삭제는 A가 받은 삭제 영수증을 B의 신원으로 재사용하는 방식으로 시도한다.

## 시험이 찾아 고친 문제

- **스트리밍 두 경로(`POST /database/execute/stream`, `GET /dataset/:id/stream`)가 소유자에게도 502**: 원인이 둘이었다. (1) 업로드 파일 소스(DuckDB)에는 knex 클라이언트가 없어 `knex: Unknown configuration option 'client' value duckdb`로 500이 났다. 운영 허용 소스가 파일·샘플이라 데이터셋 스트리밍(`useStreamingData`)이 파일 소스에서는 동작한 적이 없다. (2) 핸들러가 `Transfer-Encoding: chunked`를 직접 지정해, 오류 응답(`res.json`)이 `Content-Length`와 함께 나가면 nginx가 `upstream sent "Content-Length" and "Transfer-Encoding" headers at the same time`로 거부하고 클라이언트는 500 대신 502를 받았다. 수정: 두 컨트롤러에서 헤더 지정을 제거하고(Node가 파이프 응답을 알아서 청크한다), DuckDB 소스는 결과를 같은 NDJSON 프레임(fields, data 묶음, complete)으로 보낸다. 결과 크기는 `ANALYSIS_MAX_RESULT_ROWS`(기본 10000) 이하로 제한되고 초과하면 조용히 자르지 않고 `error` 프레임을 보낸다(대용량 스트리밍은 아니다). 스택에서 확인: 소유자 200/201 NDJSON, 없는 테이블은 `error` 프레임, 쓰기 쿼리는 JSON 오류. 단위 테스트(`connection.service.streaming.spec.ts`, `common/streaming-headers.spec.ts`) 추가. 쓰기 쿼리의 거절은 여전히 403이 아니라 500으로 나간다(핸들러가 예외를 500으로 바꿈, 이번 범위 밖).

- **위젯 상세가 소유자에게도 500**: `GET /widget/:id`가 MySQL에서 `Column 'id' in where clause is ambiguous`로 실패했다(`.subQuery()` 누락. SQLite 단위 테스트에서도 같은 코드가 실패함을 확인). 위젯 편집 화면이 깨지는 기능 결함이다. 수정하고 실DB 테스트(`widget-find-one.spec.ts`, 수정 전 코드에서 실패함을 변형으로 확인)를 추가했다.
- **차트·템플릿 카탈로그를 아무 로그인 사용자가 쓰기 가능**: 소유자 개념이 없는 전역 카탈로그라서 한 사용자가 모두의 컴포넌트·템플릿을 바꾸거나 삭제할 수 있었다. 쓰기·템플릿 전체 CRUD를 운영자 가드로 바꿨고, 제품이 쓰는 `GET /component`·`GET /component/:id`·`POST /template/recommend|dashboard`는 로그인 사용자에게 그대로 열어 두었다.
- **익명 이벤트가 타인 명의로 저장**: 인증 없는 이벤트 수집 두 곳이 페이로드의 `userId`를 믿고 저장해 피해자의 이벤트 피드에 보였다. 검증된 JWT 신원만 쓰도록 바꿨다.
- **운영에서 데모 계정·진단 엔드포인트 노출**: `GET /`가 `guest / Admin!@12`를 알려 주고 `/ip`(제3자 호출)·`POST /`(에코)·`POST /seed`가 익명으로 열려 있었다. `NODE_ENV=prod`에서는 데모 정보를 빼고 나머지는 404로 막았다.
- **BI 탐색 카탈로그의 소스 존재 신호**: `POST /bi/explore/catalog`가 남의 소스 id(403)와 없는 id(404)를 다르게 답했다. 권한 확인 전에 스냅샷을 먼저 잡던 순서를 고쳤고, 스냅샷 단계에서 없는 소스를 403으로 통일했다(다른 경로의 같은 순서에도 적용).

## 확인하지 못한 것·알고 있는 위험

- **시험하지 않은 경로**: 커머스, 백그라운드·배치 작업, 기업(조직) 기능 전체, 익명 공유·게시 링크의 토큰 경로, 리믹스·받은 항목, 내보내기 작업, 초대 가입 외의 계정 생성 경로(없음을 코드로만 확인), WebSocket. 이들은 정적 감사로만 보았다.
- **`captureDuckDBSnapshot`의 근본 원인은 그대로**: 호출자가 먼저 권한을 확인해야 한다는 계약인데 약 40곳이 그렇게 하지 않는다. 이번에는 `catalog`의 순서를 고치고 스냅샷 단계의 NotFound를 403으로 통일했을 뿐이다. 복호화·설정 읽기가 권한 확인보다 먼저인 호출자와 아래의 소스 종류 신호가 남아 있다. 정상 소유자가 방금 지운 소스를 부르면 404 대신 403 `data access denied`를 받는 작은 동작 변화가 있다.
- **익명 토큰 경로**: `JwtAuthGuard` 자체가 계정 없이 공유 링크 토큰(`Authorization-url`)으로 `GET /database/data`·`/v1/database/data`를 통과시킨다. 공유 대시보드의 데이터셋으로 제한되고 소유권 검사가 이어지지만, 계정 없는 접근 경로이며 이 시험은 보지 않았다. `GET /studio/publications/:token`(비인증 읽기)도 마찬가지다. 둘 다 별도의 "공개 링크 노출" 게이트에서 다룬다.
- **분석 이벤트**: 익명 엔드포인트는 이제 `userId`를 저장하지 않으므로 `GET /analytics/dashboard/user-events`는 `events/batch` 이벤트만 보인다(의도한 변화). 호출자가 주장한 `userId`는 `metadata`/`properties` JSON 안에는 그대로 남는다.
- **기존 QA 계약 시험**: `frontend-web/qa/api-contracts.spec.ts`의 TEMPLATE-01, COMPONENT-01/02는 일반 사용자의 카탈로그 쓰기를 기대했으므로 "일반 사용자는 403"을 기대하도록 바꿨다(실행하지 못했다: 이 QA 스택을 이번에 올리지 않았다). `backend-api/test/*.e2e-spec.ts`·`QTT-*`와 k6/artillery 스크립트도 이 경로를 쓰지만 `npm test` 범위 밖이라 갱신하지 않았고, 운영자 계정이 필요하다.
- **소스 종류 신호**: 남의 소스가 DuckDB가 아니면(예: 가입 시 만들어지는 샘플 SQLite) 일부 BI 경로가 403이 아니라 400 `not a DuckDB source`를 줄 수 있어 id의 소스 종류가 드러난다. 데이터 노출은 아니다.
- **기업 등록 API**(`POST /enterprise/enrollment`)는 임의 조직 번호에 대해 조직 이름을 돌려주고, 없는 번호는 400으로 구분한다. 여러 고객이 조직을 만들면 서로의 조직 이름을 번호 추측으로 볼 수 있다. 화면(조직 확인 문구)이 이 응답을 쓰고 있어 **제품 결정이 필요한 열린 항목**이다(기업 기능을 베타에서 끄거나 응답에서 이름을 빼는 방안).
- **지표 이름 존재 신호**: 지표 이름이 전역 유일이라 남의 지표 이름을 시도해 보면 거절 여부로 알 수 있다.
- **진행률 소켓**: `X-Socket-Id`를 검증하지 않아 소켓 id를 아는 호출자가 그 소켓에 가짜 진행 이벤트를 보낼 수 있다(남의 진행률을 읽을 수는 없다).
- 마운트되지 않은 모듈(`job-queue`, `query-timeout`, `batch-processing`, `cache`)은 소유권 검사가 없다. 지금은 아무 모듈도 불러오지 않으므로 닿지 않지만 마운트하면 안 된다.
- 이 시험은 단일 VM·단일 인스턴스, 소스 허용 유형 `file,sample`, 호출 한도 아래로 속도를 조절한 환경이다. 경쟁 상태나 대량 요청, 캐시 적중(운영 기본값은 결과 캐시 꺼짐)을 겨냥하지 않았다.
- `audit`(커밋 `a60292f4`, 격리된 작업 트리, Node 26.12.1): 백엔드 `npm test` 318 스위트 통과·12 건너뜀(MySQL 전용 스펙), 5591 테스트 통과·184 건너뜀, 실패 0. `npm run build` 오류 없음. eslint 오류 0(경고 32, 신규 여부는 확인하지 않음). 변형 확인 두 건 모두 해당 테스트가 실패했다: `.subQuery()` 제거 → `widget-find-one.spec.ts` 실패(`ambiguous column name`), 컴포넌트 컨트롤러 클래스 가드 제거 → `route-inventory.spec.ts` 2건 실패.
- 스트리밍 수정 뒤 프로브를 다시 돌려 PASS(43개 B 403, 소유자 대조 24개).
- `architect` 검토(코드 읽기만, 실행 없음): 코드 수정은 안전하고 데이터를 새게 하지 않는다고 봤으나, 위 "증명" 표현이 시험의 빈틈보다 앞서 있다고 지적했다(비동기 모듈 누락, 가드 하위 클래스를 인증으로 셈, 프로브가 어떤 거절도 통과시킴, 경로별 대조 부족, 재실행 절차가 운영 스택을 가리킴, QA 시험 깨짐). 모두 이 문서의 시험 설명 그대로 고쳤고 프로브를 다시 돌려 통과했다. 이 수정 이후의 `audit` 전체 재실행은 아직 하지 않았다.
