# 공유 → 포크(복제) 유스케이스 검증

2026-10-25 · develop `a279fbcc`. 사용자 요청: "공유하고 그걸 포크해서 다시 사용하는 유스케이스가 중요하다. `../skb-taste`를 참고하라고 했다. 분석해서 진행이 충실히 이루어졌는지 검증해 달라." 범위는 **검증과 보고까지**이고 코드는 고치지 않았다.

## 결론

- **핵심 동작은 실제 두 사용자·세 사용자 실행으로 확인했다.** 게시 → 복제 → 독립 편집 → 회수·삭제 후 사본 생존 → 재공유가 모두 동작한다. skb-taste는 취소하면 사본을 제거하는 것(UC-006 A4)과 취소 후 재공유가 유니크 키와 충돌할 수 있다는 것(GAP-011)을 승인할 정책으로 남겨 두었는데, VanillaMeta는 **사본 보존·재게시 허용**을 택했다. skb-taste 쪽은 실행한 적이 없으므로(TC 전부 미실행) "결함을 재현하지 않았다"가 아니라 **명세와 다른 정책을 택했다**가 정확하다. 이 정책이 맞는지는 사용자 승인이 필요하다.
- **빠진 것이 세 가지 있다.** (1) 사본에서 원본으로 가는 **계보가 전혀 없다**(skb-taste는 한 단계 출처를 남긴다). (2) 링크 공유 경로에는 skb-taste가 요구하는 **받은 목록·소유자 쪽 수신자 목록·알림·방문 표시**가 없다(조직 전달 경로에는 일부가 있고 이번에 실행하지 않았다). (3) 독립성·회수 후 사본 생존·재공유·TC-003 여정을 **단언하는 자동 테스트가 없다.** 지금 동작은 맞지만 회귀를 막아 주는 장치가 없다.
- **수정 후(커밋 `128f43a2`·`a2c4e1cf`·`af11aeba`·`82244c69`·`91cd33d8`와 이후 보정)**: 사용자별 throttle, 화면 실패 구분, 서비스 수준 여정 테스트 16개가 들어갔다. 실제 스택은 다시 띄워 실행하지 않았다. 503 큐 포화는 아직 열려 있다. 자세한 내용은 맨 아래 "수정 후 상태" 절.
- 이번 검증은 개발 머신 compose 스택에서 했다. 운영 URL, 실제 LLM, 실기기, 고객 데이터에서는 실행하지 않았다.

## 기준과 방법

- **기준**: skb-taste는 VanillaMeta와 별개의 저장소(SK브로드밴드용 SKB TASTE)다. "vm-skb"라는 프로젝트는 없다. skb-taste 저장소에서 이 이름은 `backend/src/main.ts:59`의 개발 CORS 호스트(`vmskb.vanillabrain.com`) 한 곳에만 나오고, VanillaMeta 저장소에는 이 문서 말고는 없다. 이 유스케이스의 명세는 `docs/use_cases/UC-006-share-targeting-projects.md`, `docs/functions/FUNCTION-014/026/030`, `docs/test_cases/TC-003-edit-independent-shared-analysis.md`, `_docs/프로젝트_공유기능_구현계획서.md`다. 모델은 "공유 = 받는 사람 소유의 독립 사본, 동기화 없음, 데이터 행은 복사하지 않음"이다. skb-taste의 TC는 모두 Draft·미실행이므로 이것은 실행 결과가 아니라 명세 기준이다.
- **방법**: 요구를 R1~R19로 나누어 (1) 코드·스펙을 읽고 근거를 찾는 정적 판정(병렬 에이전트 3개의 workflow), (2) 대상 커밋의 관련 테스트 실행, (3) 실제 스택에서 사용자 3명과 익명으로 API 시나리오 F1~F11, (4) 브라우저로 화면 시나리오 U1~U9를 했다. 정적 판정의 근거 행(파일·줄·테스트 이름)은 작업 스크래치에만 있고 저장소에는 요약만 넣었다.
- **환경**: compose 프로젝트 `vm-m25`(`NODE_ENV=prod`, `SIGNUP_MODE=invite`, 샘플·파일 소스만, 모의 AI 제공자). 스택의 api는 `52bb0d78`이다. `52bb0d78`과 `a279fbcc`의 백엔드 차이는 AI 호출 오류 처리·로그(`ai/`, `studio-creation.service.ts`의 propose 오류 처리 8줄, `studio-run.service.ts`), 운영 가드의 `AI_PROVIDER` 대소문자 처리, 운영 compose 환경변수 1개(`GOVERNANCE_AI_ENABLED`)이고, 프런트엔드 차이는 요청 제한 문구 3개 파일이다. 게시·복제(`studio-publication*`, `studio-remix*`, `studio-received-remix*`)·BI 재사용·share-url·enterprise 소스 파일은 두 커밋에서 같다(`git diff --quiet`로 확인). 웹은 `f214b678` 기준 빌드다.

## 수정 후 상태 (단위 테스트 기준, 실제 스택 재실행 전)

대상은 `128f43a2`(throttle), `a2c4e1cf`(화면 실패 구분·뒤로가기·재게시 만료·집계 경고·44px), `af11aeba`(여정 spec), `82244c69`(읽기 시각 제외·포맷), `91cd33d8`(429 문구·게시 대화상자 보정)다. 재실행하면 미리보기·저장이 사용자당 분당 30회를 넘을 때 429가 나온다. 근거는 커밋 diff와 단위·서비스 테스트뿐이다. 개발 스택은 내려 두었고 **수정 후 다시 띄워 실행하지 않았다**. 이 커밋들의 테스트 통과 여부는 이 문서에 적지 않았다. 위 실행 결과의 숫자는 `a279fbcc` 기준 원래 실행이며 그대로 둔다.

### 격차별 변경

- **F11 throttle (503은 OPEN)**: `remix` 프리셋을 추가했다. 기본 사용자별 분당 30회(미리보기와 저장을 따로 센다. 복제 화면은 블록 제외를 바꿀 때마다 미리보기를 다시 부르므로 10회는 정상 사용도 막을 수 있어 30으로 올렸다), 환경변수 `USER_THROTTLE_REMIX_PER_MIN`. 미리보기·저장 라우트(`studio-remix.controller.ts`, `studio-received-remix.controller.ts`)에 걸었고, 운영 부팅 검사와 `deploy/docker-compose.prod.yml`, `deploy/.env.prod.example`에 넣었다. throttle 단위 테스트(`user-throttle.guard.spec.ts`, `user-throttle-coverage.spec.ts`, `studio-remix.controller.spec.ts`)를 고쳤다. 병렬 503 `analysis worker busy`는 사용자별 제한과 무관한 분석 큐 포화다(`backend-api/src/analysis/duckdb.service.ts:537`, 큐 상한 `ANALYSIS_MAX_QUEUE`, 기본 16). **남아 있다(OPEN).** 결정할 것: 응답에 `Retry-After`를 붙일지, 분석 워커·큐 상한을 얼마로 할지. 공유 큐 포화를 429로 바꾸는 것은 원인과 맞지 않아 이 문서는 권하지 않는다.
- **U1 재게시 만료·집계 공개 안내 (코드 수정, 화면 재확인 전)**: 재게시 대화상자가 이전 만료를 채우지 않고 비워서 시작한다(서버는 빈 값이면 기본 기간을 쓴다). 링크 공개를 고르면 집계 숫자(차트 최대 500행, KPI 추세 점)가 링크 소지자에게 보인다는 경고를 띄운다. 만료 문구도 고쳤다(`StudioPublish.tsx`).
- **U7 복제 불허 링크 오류 (코드 수정, 원인 재현 미확인)**: 템플릿 요청과 원본 목록 요청을 `Promise.allSettled`로 나눴다. 템플릿이 거절(403·404·410)하면 목록 실패보다 그 사유가 화면을 정한다. `remixFailure()`가 사유별 문구, 재시도 가능 여부, 원본 없음 여부를 준다. 원본이 없으면(404·410) 뒤로가기 링크를 숨긴다. 403 문구가 화면에 보이지 않던 원인은 재현하지 않았다.

- **U8 390px 44px (CSS 수정, 재측정 전)**: 900px 미만에서 복제·게시 대화상자의 버튼과 라벨 행의 최소 높이를 44px로 했다. 매핑 선택 상자는 AGENTS.md TC050 결정에 따라 36px로 둔다. 체크박스·라디오 자체는 16px이고 라벨 행이 터치 영역을 넓힌다. 브라우저에서 다시 재지 않았다.
- **계보(R7)**: 변경 없음. 설계 결정이 먼저다.
- **새 requestId 중복(R3)**: 정책은 바뀌지 않았다. 새 requestId는 별도 사본을 만든다는 현재 동작을 spec이 `PENDING POLICY`로 고정했다. 정책이 바뀌면 이 테스트도 바꿔야 한다.

## 실행하지 못한 것

- **저장 도중 재시작·크래시 복구**: 재시작을 금지해서 하지 않았다. 코드 분석과 동시 5건만 했다.
- **MySQL 의존 스펙 20개**(받은 복제 복구 14, BI 재사용 MySQL 1, 통합 5): 건너뜀이며 통과가 아니다.
- **조직 수신 경로(받은 분석 복제)의 실제 복제**: 조직·전달을 만들어 실행하지 않았다. 조직 없는 사용자의 안전한 오류 화면과 governed 정책 거부만 확인했다.
- **pivot 블록이 있는 대시보드의 복제 거부**와 **레거시 BI 재사용·`share-url` 경로의 실제 실행**.
- **만료(회수 아님) 링크의 화면**, 768px에서 복제 마법사 전체, 실기기, Safari·Firefox, 접근성 점검.
- **운영 URL·실제 LLM·고객 데이터**: 이 검증과 무관하게 아직 없다(`customer-pilot.md`는 NOT_RUN).
- **단위 테스트 통과가 실제 단언인지 전수 확인**: 정적 판정 에이전트가 각 요구에서 단언하는 테스트 이름을 찾았지만, 모든 행을 사람이 다시 열어 보지는 않았다.
