2026-10-15, 기준 `f427f9e4` 위 UC017 변경, P3. AIWF UC·설계·TC·계획을 먼저 작성하고 별도 native executor의 의미 대조 후 구현했다. Draft·pin/packet·사람 승인·운영 배포·전체 제품 수용은 별개다.

409는 p1의1번 제목을 “전체 요청 수 · 내 복구”, p2의같은 제목을 “전체 요청 수 · 최신 창”으로 바꾸고 p2에서 비대상3번 제목도 “평균 입찰가 · 최신 보존”으로 저장해 만들었다. p1의 질문은 “충돌 후에도 보존할 질문”이다. 409 후 GET과 명시 선택을 거쳐 p1 제목·p2의 비대상 제목을 함께 유지했다. 합친 뒤 저장은 비활성이며 전체 미리보기를 다시 성공시켜야 한다. 과거 이력은 초기화하고 질문은 유지했다(`conflict-compare.json`).

응답 유실은 제품의 mock 성공 응답이 아니다. 전용 로컬 프록시에서 실제 upstream201과 revision을 받은 후 Content-Length보다 짧은 본문만 전송하고 연결을 끊었다. 실제 DB가 갱신됐으나 화면은 결과를 확인하지 못했다. 읽기 상태 확인에서 초안과 서버 SQL/표시/모든폭배치가 같음을 확인하고 저장 화면으로 이동했다. committed 응답과 복구 후 응답은 revision을 포함해 deep equal이다. 프록시 로그에유실 뒤추가POST가없는것을대조했다.

미전달 실패는 프록시가 정확히 분석22 editor POST 한 번을 upstream에 전달하지 않고503을 반환하게 했다. 확인 GET도 한 번503으로 만들고 재시도했다. 실패 전/후 분석은 revision까지같고, 복구후에는현재초안제목만변경됐다. 새 API나제품fault스위치는추가하지않았다.

실제 취소는 “현재 편집 내용을 저장해 줘.”라는 save-only 분류 요청에서 확인했다. 분류 LLM에는 질문 문자열만전달한다. 백엔드99601의직계Codex34368이시작한뒤같은Ego실행에서취소버튼을눌렀다. PID종료와저장정의/revision무변경을확인했다(`cancel-verified.json`). 취소 뒤 같은질문을재실행했고XHR은취소status0→새AI201(save)→editor201이다. reload후초안제목과동일4블록/SQL/배치가남았다. 저장전송뒤rollback을취소라고주장하지않는다.
