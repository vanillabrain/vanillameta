# UC-013 자동 질문 목적 판별 검증

2026-10-15 · 기준 `747da628` 위 UC-013 변경 · P3 첫 단위. AIWF 문서와 실패 회귀를 먼저 작성했다. 선택 블록의 내용/배치를 기본 자동 판별하며 수동 목적은 접힌 고급 설정에 남긴다. 저장·게시·복제·다중 블록 실행까지 완성한 것은 아니다.

## 실행 결과

Ego TaskSpace11에서 공개 Rill source7의 검증 분석22만 편집했다. 기존 Codex/gpt-6-luna 설정을 사용했고 모델을 대체하지 않았다. 설정 확인은 독립 모델 attestation과 구분한다.

1. 390px에서 복사본 `모바일 연속 요청 수`를 선택하고 목적 선택 없이 소수2자리 변경을 요청했다. content 응답201, 내용 AI 안내, 고급 설정 접힘을 확인했다.
2. 같은 입력창에서 “선택한 블록을 아래로 한 칸 옮겨 줘.”를 요청했다. 아래의 초기 오류 수정 뒤 layout 응답201과 mobile `{x:0,y:10,w:4,h:3}`→`{x:0,y:11,w:4,h:3}`를 확인했다.
3. 두 번 undo에서 y10·소수1자리, 두 번 redo에서 y11·소수2자리로 돌아왔다. 내용/배치가 공통 이력을 사용한다.
4. “제목을 새로운 요청 수로 바꾸고 동시에 오른쪽으로 한 칸 옮겨 줘.”는 한 가지 변경을 구체화하라는 고정 안내로 끝났다. 입력·좌표는 전후 동일하고 저장은 비활성이었다. 이후 undo 한 번이 바로 y10으로 돌아가므로 clarify가 이력을 추가하지 않았다. redo 후 기존 서버 미리보기를 다시 실행했다.
5. 실제 저장 버튼→분석 화면→브라우저 reload를 실행했다. 4개 unique block ID, 복사본634.51M과 추세, exact634513000이 유지됐다. 전후 analysis API 전체 응답을 deep 비교했으며 revision 외 차이는 해당 복사본의 decimalPlaces1→2와 mobile y10→11뿐이다. 원본3개·SQL·제목·다른 폭·layoutSizes는 동일하다.
6. 390/1440px 편집 화면을 캡처·실측했다. 질문 입력32px·버튼28px·글꼴12px, 가로 넘침0, 고급 목적 기본 접힘이다. 390은 세로 배치,1440은 입력/버튼 중앙 정렬이다. 실제 휴대폰 검증은 아니다. 지정 y11 아래의 공백은 테스트 배치 결과이며 기본 밀도 권장값이 아니다.

Rill 공식 데모 데이터의 기존 전체 기간635M/$5.57 비교 증거를 재사용했다. SQL·데이터 집계는 바뀌지 않았고 복사본 표시 정밀도만 바뀐다. 이번에 Rill 화면을 다시 조작하거나 대화 편집 기능의 동등성을 주장하지 않는다.

## 발견한 오류와 수정

- 자동 내용 요청은 분류+생성이 순차 실행되어 기존 axios 기본10초 제한에 걸렸다(status0·약10002ms). editor AI 요청에만 기존 AI 화면과 동일한180000ms를 전달하도록 수정했다. 설정 전달 회귀를 먼저 실패 확인했다. 같은 AbortSignal과 늦은 응답 토큰 검사는 유지한다.
- 초기 배치 요청은400으로 실패했고 재시도201도 y10→13으로 이동해 “한 칸” 의미와 달랐다. 성공 응답을 PASS로 세지 않았다. 해당 배치만 undo로 복원했다. LLM 입력을 selectedRect와 다른 블록의 occupiedRects로 분리하고 제목을 제외했다. 한 칸은 블록 높이가 아닌 grid1이라는 규칙과 y10→11 예시를 보강했다. 최종 코드에서 같은 기본auto 질문을 다시 실행해 정확한 y11과 저장/reload를 확인했다. 임의 배치 문장 전체의 정확성은 미검증이다.
- 백엔드 재기동 시 기존 런타임 override가 빠져 인증/소스 해독 오류가 발생했다. 원래 검증 런타임 설정을 그대로 복원해 해결했다. 기존 DB의 암호화 설정은 변경하지 않았다. 다른 프로젝트3000/4000 서버는 종료하지 않았다.
