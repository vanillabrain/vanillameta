# UC-016 다중 블록 변경 검증

2026-10-15, 기준 `01d707d0` 위 UC-016 변경, P3. AIWF UC·설계·TC·계획을 먼저 작성하고 별도 native executor의 의미 대조 후 구현했다. 문서 상태는 Draft이며 사람 승인, 운영 배포, 전체 제품 수용과 구분한다.

공개 Rill source7·분석22(4블록), 기존 4898/4899/3698 서버, Ego TaskSpace20, 지정 Codex/gpt-6-luna 설정을 사용했다. 다른 서비스와 사용자 세션 자료는 정리하지 않았다. 증빙은 `/tmp/vm-batch/`, `/tmp/vm-batch-*.log`와 로컬 `.aiwf/evidence/UC-016/`에 있다. 임시 파일의 영구 보관은 보장하지 않는다.

첫 질문은 “1번 차트의 소수 자릿수를 1자리로 바꾸고, 2번 차트의 소수 자릿수를 2자리로 바꿔 줘.”였다. 저장 후 정의는 두 decimalPlaces와 revision만 다르고 SQL·비대상·모든 폭의 배치는 같았다.

부분 실패 질문은 “1번 차트의 소수 자릿수를 3자리로 바꿔 줘. 그리고 4번 차트는 현재 너비와 높이를 그대로 유지하면서 오른쪽으로 2칸 이동해 줘.”였다. 첫 내용 변경 뒤 4번 배치가 실패했다. 응답은 필터로 감싼 `data.batchFailure:{stage:'change',position:4}`였고 화면에 전체 미적용과 질문 수정 안내가 표시됐다. 소수 자릿수 1/2/2/0, undo 비활성, 저장 요청 0회와 전체 저장 정의·revision 일치를 확인했다.

질문을 4번 왼쪽 한 칸으로 고쳐 재시도했다. 단일 undo는 1번 소수 3→1자리와 4번 desktop x0→1을 함께 되돌렸고 redo도 함께 복원했다(`live-history.json`). 저장/reload 후 대상 변경만 유지됐다. 2·3번, 모든 SQL, 모바일·태블릿 배치는 보존됐다.

명시 저장을 포함한 다중 질문은 AI201 batch/true·전체 미리보기 뒤 editor201 한 번으로 이어졌다. 다만 최초 실행에서 LLM이 대상2 제목을 임의로 바꿔 결함으로 기록하고 아래처럼 수정했다. 최종 제목 보존 보강 후 다시 실제 다중 표시 질문을 실행했다. 저장/reload 결과는 소수 1/4자리, 원래 두 제목, 비대상·모든 SQL/배치 보존이다(`final-compare.json`).

SQLite 원자성 테스트는 테스트 전용 DB에서 두 번째 DashboardWidget INSERT에 trigger ABORT를 주입했다. 앞서 생성한 Dataset/Widget과 연결·Dashboard 갱신이 모두 rollback됐다. 6종 엔티티 count와 `analysis(includeRevision=true)` 전체가 이전과 같았다. trigger는 finally에서 제거했으며 운영 DB에는 주입하지 않았다.

## 디자인

기존 AnalysisUi 토큰을 재사용하고 질문 패널 아래 12px 변경 요약을 추가했다. 최종 “함께 저장할 수 있습니다” 문구를 포함한 390/768/1440px 실제 캡처를 직접 검토했다. 입력 외곽 32px, 버튼 28px, 글꼴 12px, 가로 넘침 0px이다. 데스크톱·태블릿에서는 같은 행의 중앙에 정렬되고 390px에서는 입력·버튼이 세로로 배치된다. 요약은 인접 설정·카드와 겹치지 않으며 목적 설정은 접혀 있다. 오류 화면도 390/1440px에서 같은 크기·넘침 0으로 안내가 줄바꿈된다. 기능 PASS와 대표 디자인 PASS를 구분하며 실제 기기·모든 상태·전체 접근성은 검증하지 않았다.

초기 폭 전환 직후 차트 resize가 끝나기 전에는 768/390px에서 overflow 168/173px를 읽었다. DOM 경계와 실제 캡처를 확인하고 레이아웃 안정 조건을 기다린 뒤 0px로 재측정했다. 최초 입력 측정은 접힌 radio를 잡았으므로 실제 질문 TextField 외곽으로 대상을 고쳤다. 이 관측 오류를 제품 통과 근거로 재사용하지 않는다.

## 발견과 수정

1. 처음 100칸 이동 질문은 분류 단계 clarify로 끝났다. 부분 실패 검증으로 세지 않았다. 불가능해 보이는 요청도 서버 검증으로 보내도록 지침을 보강하고 실제 경계 초과 질문으로 change 실패를 검증했다.
2. 소수만 바꾸는 명시 저장 질문에서 LLM이 복사 KPI의 제목까지 바꿨다. batch 내용 action에 제목/이름/title/rename 변경이 없으면 서버가 기존 제목을 유지하도록 고쳤다. 드리프트를 반환하는 보존 회귀와 명시 rename 허용 회귀를 추가했다. 분석의 원래 제목은 UI 미리보기·저장으로 복구했으며 마지막 실제 질문·저장/reload에서도 제목 보존을 확인했다. 모든 자연어 의미 보존을 보장하는 것은 아니다.
3. 독립 FE 리뷰 후 main이 실제 HTTP envelope의 오류를 읽도록 수정했다. 수동 저장의 배치 안내는 기존 errorMessage를 재사용한다. 저장 전 요약은 “함께 저장할 수 있습니다”로 고쳤고 동일 결과는 변경·undo가 생겼다고 안내하지 않는다. 이후 main이 회귀를 검증했으며 별도 재승인은 주장하지 않는다.
4. 과거 UC013/014/015의 다중 clarify 계약에 UC016 확장을 연결했다. 실패 position은 현재 items의 1-based 번호이고 모든 배치는 단일 layoutMode를 사용한다. 배치 동작에 폭을 명시하는 질문은 clarify다. 블록 제목에 포함된 “모바일”은 폭 지시와 구분한다.
