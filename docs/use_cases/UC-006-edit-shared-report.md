# 유스케이스: 공유 리포트 편집

## 개요

**유스케이스 ID:** UC-006  
**유스케이스명:** Edit Shared Report  
**주 액터:** 수신자  
**목표:** 공유 리포트의 위젯, 레이아웃, 제목을 제자리에서 수정해 협업 결과를 리포트에 반영한다  
**시작 이벤트:** 에디터 링크를 가진 수신자가 공유 리포트의 편집을 선택한다  
**상태:** Draft

**Requirements:** [FR-006, NFR-007, NFR-008, C-004](../requirements.md)

## 사전 조건

- 수신자가 에디터 역할의 공유 링크를 보유하고 로그인한 상태다
- 공유 리포트가 존재한다

## 주 성공 시나리오

1. 수신자가 공유 리포트를 열고 편집을 시작한다.
2. 수신자가 리포트 — 위젯, 레이아웃, 제목 — 를 수정한다.
3. 수신자가 변경을 저장한다.
4. 시스템이 커밋 시점에 링크의 활성 상태와 에디터 역할을 다시 확인하고, 새 상태를 새 리비전으로 기록해 현재 리비전으로 지정한다.
5. 리포트를 보는 모든 사람이 갱신된 상태를 본다.

## 대안 흐름

### A1: 유효하지 않은 변경

**트리거:** 수정이 검증에 실패한다 — 예: 삭제된 데이터셋을 참조하는 위젯 (3단계)  
**흐름:**

1. 시스템이 저장을 거부하고 문제를 설명한다.
2. 수신자가 변경을 수정하거나 버린다.
3. 3단계에서 계속하거나 유스케이스 종료.

### A2: 동시 편집

**트리거:** 수신자가 저장하는 순간 다른 에디터의 저장이 이미 새 리비전으로 커밋돼 있다 (4단계)
**흐름:**

1. 시스템이 수신자의 저장을 한 번만 수용해 새 리비전으로 기록하고 현재 리비전으로 지정한다 — 앞서 커밋된 리비전도 그대로 보존된다(last-write-wins).
2. 시스템이 동시 변경을 덮어썼음을 수신자에게 알린다.
3. 5단계에서 계속.

### A3: 수신자가 변경 폐기

**트리거:** 수신자가 저장 없이 편집을 그만둔다 (2–3단계)  
**흐름:**

1. 시스템이 저장되지 않은 수정을 버린다.
2. 유스케이스 종료.

### A4: 커밋 시점에 권한 소실

**트리거:** 저장 시점에 링크가 만료·철회됐거나 에디터 역할이 아니게 됐다 (4단계)
**흐름:**

1. 시스템이 저장을 거부하고 사유를 알린다 — 리포트와 기존 리비전은 변하지 않는다.
2. 유스케이스 종료.

## 사후 조건

### 성공 사후 조건

- 공유 리포트가 저장된 수정을 반영한다
- 이전 상태들이 복원 가능한 리비전으로 보존된다
- 리포트의 공유 링크, 에디션, 소유권은 변하지 않는다

### 실패 사후 조건

- 리포트의 저장된 상태는 변하지 않는다
- 기존 리비전들은 그대로 유지된다

## 비즈니스 규칙

### BR-001: 에디터는 신원이 필요하다

공유 리포트 편집은 로그인 계정을 요구한다 — 모든 변경이 귀속되어야 하므로,
익명 열람이 익명 편집을 의미하지는 않는다.

### BR-002: 모든 저장은 이력을 남긴다

각 저장은 새 리비전을 만들고 이전 리비전들을 모두 보존한다 — 어떤 편집도
되돌릴 수단을 파괴하지 않는다.
