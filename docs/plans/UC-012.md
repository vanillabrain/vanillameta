# UC-012 — P2 지표·차원 제안/재사용 구현 계획

상태 Draft. FR-007/008·NFR-004. 현재 단계는 설계 완료/구현 전이다. [UC](../use_cases/UC-012-semantic-creation.md), [설계](../architecture/semantic-creation.md), [TC](../test_cases/TC-012-semantic-creation.md)를 기준으로 한다.

## A — 쓰기 없는 제안·서버 컴파일

- `bi` 아래 구조화 제안 validator/compiler를 둔다. 기존 metricFields/metricExpression·source profile·활성 지표 검증·dashboard preview를 재사용한다.
- 기존 AiService.callLlm으로 SQL이 아닌 지표/원본 차원/블록 제안을 얻는다. schema와 소유 카탈로그만 제공한다. canonical 정규형과 재사용 계획·sourceRevision·previewDigest를 만든다.
- metric definition을 받는 내부 prepare 경계를 재사용 가능하게 최소 분리하되 저장 지표 권한 경계를 완화하지 않는다. 새 지표를 먼저 저장해서 기존 prepare를 호출하지 않는다.
- 단계 A는 API/단위 개발 체크포인트다. 저장 구현 전 고객 UI에 “새 지표도 함께 저장된다”는 약속을 노출하지 않는다.
- 검증: TC01/02/04/05/11, 기존 저장 지표 재사용/계산/미리보기 회귀. 실제 Luna의 Rill 질문과 독립 정답 대조.

## B — 원자 저장·재시도와 기존 분석 연결

- 신규 AnalysisCreationReceipt entity/migration: actorId+requestId unique, payloadDigest, dashboardId, createdAt. 현재 DB를 초기화하거나 과거 지표 이름을 일괄 변경하지 않는다.
- 기존 Metric.name unique에 들어갈 deterministic 내부 이름, 유효 legacy 정의 동등 비교, 비활성 충돌, 저장 직전 PLAN_CHANGED를 구현한다.
- 같은 metadata manager로 신규 지표·기존 structured-bi-dashboard snapshot·AiDashboardService.save(sharedManager)·영수증을 저장한다. source snapshot/revision과 metric version을 재확인한다. pinned DuckDB context의 버전 조회를 최신 소스 확인으로 오인하지 않도록 공유 manager의 현재 원본 포인터 비교를 테스트한다.
- 신규 UUID blockId·dimensionDefinition을 기존 snapshot에 연결하고 metric-analysis-links·UC003/004·P1 편집 경계를 회귀한다.
- 검증: TC03/06/07/08/09/12. 실제 SQLite DB transaction/동시 요청·실패 주입을 사용하고 모킹만으로 원자성/중복0 PASS를 보고하지 않는다. migration은 기존 DB 보존과 downgrade/rollback 경계를 확인한다.

## C — 기존 질문 UI 연결·출하 검증

- 기존 AI 분석 만들기에 canonical 제안/미리보기/저장 결과를 연결한다. 기본은 결과와 저장이며 계산 기준은 접는다. 별도 모드/엔티티 생성 마법사는 추가하지 않는다.
- 저장 클릭의 requestId를 동일 payload의 네트워크 재시도에 유지한다. payload/source 변경은 새 미리보기를 요구한다. 오류/취소 때 질문과 마지막 유효 결과를 유지한다.
- TC10의 실제390/768/1440 화면·XHR·저장·새로고침과 Rill 수치/표시 대조를 수행한다. 현재 auto-review 거절을 다른 browser/native 경로로 우회하지 않는다. 실행이 거절되면 해당 gate를 BLOCKED로 유지한다.

## 검사·종료 조건

A/B/C를 구현한 변경 범위의 BE unit/DB integration → FE component/type/lint/build → 실제 지정 LLM/API → 허용된 UI 검증을 수행한다. 기존 정상 데이터 업로드/조회 전체를 매번 반복하지 않는다. 세부 파일명은 구현 시 현재 구조를 재확인한다. 예상 명령은 backend-api `npm test -- --runInBand <관련 spec>`/`npm run build`, frontend-web `npm test -- <관련 test>`/`npx tsc --noEmit`/변경 eslint/`npm run build`다.

이번 설계 단위의 종료는 UC/BR/TC/엔티티·용어·현재 코드 대조/미결정 없는 첫 범위·실행 계획·문서 검사·pin/packet·commit/push다. 전체 P2의 종료는 A/B/C와 TC-012 실행이며 설계 완료와 구분한다. 고객 승인·독립 리뷰·운영 DB 검증은 별도 증거가 필요하다.
