# UC055 사용처 기반 삭제 보호 후속

## 현재 확인과 범위

개인 보관/복원은 [별도 구현 계획](UC-055-library-archive.md)을 따른다. 이번 조사에서 `DashboardService.remove`가 dashboard→widget 연결→단일 userMapping→share를 서로 다른 쓰기로 지우며, controller의 소유 확인 후에는 현재 권한/정의/참조를 다시 검사하지 않는 것을 확인했다. 이를 참조 중 자산 삭제 보호나 원자 삭제 완료로 표시하지 않는다.

## 구현해야 할 계약

- 영향 조회와 명시 삭제를 분리하고 현재 actor/활성 계정·조직·소유권/JWT epoch를 재검사한다. 조직·수신자 이름/토큰/CSV/SQL을 영향 응답에 노출하지 않는다.
- 대시보드의 현재 직접/그룹 공유·grant·live 공유·Studio/기존 게시와 다른 원본 참조를 현재 상태로 조사한다. 독립 복사본과 원본을 참조하는 사용처를 구별한다. 이미 독립된 복사본을 자동 삭제하거나 삭제 거절 사유로 잘못 묶지 않는다.
- 사용 중 삭제는 안전한 사용처 종류/개수·수동 해결 경로로409이며 자동 연쇄삭제0이다. 소유자가 개인 보관을 대안으로 선택할 수 있다.
- 영향 미리보기 이후 새 사용처가 생기면 삭제 직전에 검증해 거절한다. actor/User·원본/관계의 일관된 잠금과 CAS 또는 serializable 재검증을 기존 공유/게시 쓰기와 연결해야 하며 SQLite 성공만으로 MySQL 경합을 통과시키지 않는다.
- 허용된 삭제는 본인 원본과 소유 연결 행만 한 transaction에서 처리하고 원본/권한/다른 자료·파일·사본을 지키며 감사 결과를 기록한다. 부분 실패는 전체 rollback이다. 공유·게시 중지는 별도 명시 동작이며 삭제가 조용히 대신하지 않는다.
- 소스/지표 삭제·조직 비활성화의 영향 검사는 별도 자원 계약이다. 현재 직접 소스 사용처 일부를 전체 그래프 완료로 처리하지 않는다.

## 종료 증거

사용처 있음/없음·권한 부족·독립 사본·새 참조 경합·저장 중 실패에서 원본/연결/게시/사본/감사 불변 또는 허용한 원자 변경을 실제 DB/JWT로 대조한다. 영향 UI→명시 요청→409/성공→새로고침 및390/768/1440을 실제 확인한다. 이 문서는 설계이며 구현/테스트/운영 수용은 NOT_RUN이다.
