# UC053 수신자 공유 요청 새로고침 복구

Status: Draft

## 목표와 범위

FR021/NFR005/NFR008·TC050 E06/E07. 직접 직원 조회 공유/회수의 frozen UUID·active/allowCopy·수신자 CAS를 전송 전에 탭 저장하고, 접기/이동/새로고침 뒤 같은 사용자·세션 epoch·조직·대시보드에서 복구한다. 독립 복제 허용 변경은 포함하지만 독립 사본 생성과 동적 그룹 공유의 미확정 요청 복구는 후속이다. 현재 소유 admin 정책은 바꾸지 않는다.

## 계약

- sessionStorage만 사용하며 24시간/8KiB/최대50명·중복 없는 양수 ID/정수 CAS·UUID/정확한 키를 검증한다. token/직원 이름/SQL/원본/링크를 저장하지 않는다. 사용자·조직·대시보드·opaque session/auth epoch로 격리하고 로그인 변경 시 과거 응답을 적용하지 않는다. 이 cache fence는 서버 권한 검사를 대체하지 않는다.
- 저장소 기록/읽기 검증에 실패하면 새 공유 쓰기를 시작하지 않는다. 만료/손상은 자동 POST/새 UUID 재전송하지 않으며 경고한다. 이미 미확정인 요청을 최신 GET 성공만으로 삭제하지 않는다.
- reload 복구는 쓰기0이다. frozen 요청의 대상 번호/변경 종류·복제 허용 여부를 표시하고 최신 관계 GET으로 현재 관리 권한을 확인한 뒤 별도 명시 재시도 동의로 같은 UUID/내용의 POST를 보낸다. 영수증은 과거 결과이며 현재 관계/권한 증명이 아니다. 완료 뒤 최신 관계 재조회 전 새 쓰기를 금지한다.
- 기존 시도 중에도 최신 관계 읽기는 미확정 요청을 보존한다. 409/403/통신 실패는 요청을 유지하고 자동 CAS 변경/재바인딩하지 않는다. 명시 보관 해제는 서버 취소가 아니며 과거 공유가 적용됐을 수 있음을 설명하고 별도 확인한다. 다른 조직/사용자/epoch의 티켓을 가져오거나 노출하지 않는다.
- 그룹/직접 grant·원본·독립 사본·알림/감사 보존과 같은 요청의 멱등 영수증을 유지한다. 회수 후 과거 성공 요청 replay는 재공유하지 않는다.

서버 검토에서 JWT guard 이후 User 잠금 대기 중 epoch가 바뀌면 전달 POST가 이를 재검사하지 않는 공백을 확인했다. 직접 전달 controller가 authVersion을 전달하고 정렬 User 잠금 뒤·정책/영수증 분기 전에 현재 active/epoch를 검사하도록 최소 보완한다. GET 성공·FE cache 격리로 이 서버 검사를 대신하지 않는다. 실제 MySQL 두 연결의 epoch 변경 대기 거절과 관계/감사/영수증 쓰기0을 확인한다.

## 검증과 종료 조건

저장소 만료/손상/격리/용량·쓰기 거절, UI 실패→unmount/remount→GET→별도 동의→정확 replay·접기/최신 GET 보존·403/409·로그인 변경 늦은 응답 차단을 의미 있는 테스트로 확인한다. 실제 Docker MySQL의 공유 영수증/회수/replay·rollback을 선택 검증하고, Ego 한 공간에서 실제 공유/회수의 응답 유실과 새로고침 복구·쓰기0·390/768/1440px 크기/정렬을 확인한다. 비공개 합성 fixture만 사용하고 원본/직접 권한/사본 불변과 현재 수신자 접근을 대조한다. AIWF pin/check/packet·별도 검토 후 commit/push한다. 운영·실기기·전체16개 수용은 별도다.

## 변경 파일

FE Deliveries/ResourcePolicies·delivery pending 저장소/테스트·기존 API 검증, UC053/TC050·이 문서/선택 증빙·AGENTS/수용 점검. 서버 계약 결손이 확인될 경우에만 최소 서버 변경을 추가하며 그룹/복제 화면을 함께 확장하지 않는다.
