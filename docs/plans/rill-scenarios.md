## RXS03 설계 당시 계약

문제: 현재는 SUM(raw profit)/SUM(raw revenue)는 만들 수 있지만 저장된 매출·비용 지표를 조합한 이익/마진을 정의할 수 없다. 샘플 원본 profit 열을 쓰는 것만으로 지표 조합 완료라고 하지 않는다.

초기 계산 노드는 저장 지표의 `{metricId,definitionVersion}` 또는 add/subtract/ratio(left,right)다. SQL/함수명/임의 문자열 식은 받지 않는다. ratio의 배율은1/100이고 분모0은NULL이다. 덧셈/뺄셈은 같은 단위, 비율은 같은 단위를 나눠 무단위/%만 허용한다. USD/$/US$, KRW/₩/원, count/건의 동등 표기를 정규화한다. 제한은깊이4/노드31/고유 참조6이다.

서버는 소유자·같은 소스·정확한 정의 버전을 확인하고 피연산자의 구조화 정의를 고정 저장한다. 참조 지표를 나중에 바꾸어도 기존 계산이 조용히 바뀌지 않게 한다. 클라이언트가 보낸 operand 정의는 신뢰하지 않는다. 초기 helper는 FORMULA를 다시 참조하는 순환/중첩 저장 의존을 거절한다. 식 안에서 `(매출-비용)/매출`의 중첩 노드는 지원한다. 필요 시 이후 단계에서 명시 재귀 참조/의존 경로를 추가한다.

통합은 BiService의 저장/준비 → 공통 metric compiler → Explore/Pivot/CSV → Studio 참조/미리보기/저장·게시 순서다. 아직 안전하게 remap하지 않은 복제 경로는 명시 거절하며 조용히 원본 열을 대입하거나 원본 소스의 수치를 보여주지 않는다. 기존 비계산 지표/블록의 정의·ID·숫자는 유지한다. 신규 AI 정의를 열기 전 직접 제작과 저장 지표 참조가 전체 경로에서 일치하는지 검증한다.

정답: 같은 VM CSV에서 `SUM(revenue)-SUM(cost)`=2657.55 USD, 이를 `SUM(revenue)`로 나눈 백분율=17.7911416175…%. 집계 조건의8행에서는292.79 USD/5.3908400460…%. 고객 비율을 평균하지 않는다. 0/NULL/음수·빈 결과, source/revision/metric-version 충돌·권한 거절·입력 변조·기존 정의 보존을 먼저 검사한 뒤 실제 Studio/탐색/Pivot/CSV·새로고침·세폭/키보드를 실행한다. pure helper PASS만으로 이 단위를 완료 처리하지 않는다.

## RXS06 실행 계약

Given: VM 앱 전환 source5의 고정16행/UTC, 다운로드 저장 지표와 version의v1.9/v2.0. When: 두 값을 명시 선택→동시 추세→1월18일 상세→같은 시점 Pivot→복귀. Then: 전체 버전 합계840/1014, 다운로드율20%/23.2568807339…%를 각각 원본 분자/분모로 계산한다. 일별 v1.9는1월13일560/14일280, v2.0은18일854/19일160이며 나머지는NULL이다. 날짜 간격을 압축하거나 없는 날짜를0으로 만들지 않는다.18일 Pivot은 선택한 시점/원래 기간의 교집합·공통 필터·두 값·지표를 유지하며 v2.0=854, 복귀 후 선택 시점/전체 추세를 보존한다.

## RXS10 보고서→동일 조건 탐색 계약

현재 링크는 source만 열고 기본 지표/기간으로 조회하므로 동일 조건 분석이 아니다. 저장본의 단일 canonical 지표+차원 블록에서 source/metric 정의·공통 기간/typed filters를 서버가 읽어 탐색 초기 상태로 전달한다. URL에는 dashboardId/blockId/revision만 넣고 SQL/결과/토큰은 넣지 않는다. 목적지에서도 소유권·정확한 저장revision/source파일·지표정의digest를 확인하며 기본 조건 조회를 먼저 실행하지 않는다. 지표가 같은 버전 번호로 바뀐 경우도 쿼리 전에409다. 실패 시 다른 기본 수치로 대체하지 않고 명시 재확인한다.

첫 실행은 저장된 company별 이익 표→Explore KPI/동일 company 순위→원 Studio 새 탭 복귀다. 금액2657.55·6그룹 및 필터회사1763.65를 독립 대조한다. 원 Studio 질문/미저장 내용은 이동하지 않고 유지한다. 미저장 초안·원시 timestamp선·Explore가 표현하지 못하는 timestamp 정밀도 기간·다중 지표를 임의 변환하지 않는다. 이런 조건은 링크 미지원 안내이며 원본 계산을 추정하지 않는다. Pivot/CSV/다른 분석으로 확장할 때 버전 기준이 조용히 사라지지 않도록 경계/안내를 먼저 정한 뒤 연결한다. 세폭/키보드·실제409·권한을 확인 전 PASS로 올리지 않는다.

## RXS11/12 실행 계약 — 파일 교체와 수정 복구

원본 마진 보고서와 계산 비용률을, 열 이름·매출/비용 비율이 다른 고정 USD 파일로 복제한다. CSV는 repo에 배포하고 기존 샘플 준비 API/파일 업로드를 재사용한다. 정상 파일·필수 열 누락 파일·KRW 파일을 분리한다. 단위는 파일명/단순 currency 열로 추측하지 않으며 서버가 설치한 정확한 fixture checksum/현재 파일 메타데이터만 알려진 계약으로 인정한다. 알려진 통화가 다르면 환산 없이 차단하고, 알 수 없는 사용자 파일에는 동일 단위 명시 확인이 필요하다.

저장된 canonical 지표는 SQL만 복사해 연결을 버리지 않고 새 소스의 clone-local 지표로 옮긴다. FORMULA의 고정 피연산자도 새 소스/새 ID로 함께 복제한다. 임의 SQL에서 지표를 추측하지 않으며 canonical 증명이 맞지 않는 연결은 보존형 거절한다. 원본 ID/정의/배치/게시본은 불변, 새 복사본은 비공개·새 블록 ID·모든 폭 배치·표현을 보존한다. 원본 공통 필터/기간도 명시 매핑하고 미리보기/저장에 유지한다. 원자 transaction과 영수증 재시도를 재사용한다.

누락 열 상태에서 영향 블록/매핑을 보여 주고 정상 파일로 수정→전체 미리보기→명시 저장→reload한다. 블록을 제외한 결과를 오류 수정 완료로 대신하지 않는다. 실패 중 대시보드/지표 쓰기0, 사용자 제목/선택 보존, 새 데이터의 독립 Decimal 정답·Rill 같은 파일 결과·390/768/1440·키보드 실제 검증 후 해당 범위만 PASS로 올린다. 기존 정상 검사는 반복하지 않는다. 임의 자연어 자동 오류 복구/일반 통화 환산/모든 스키마 변경·운영/실기기는 후속 gate다.


RXS11/12 후속: 내 파일/clone-local FORMULA/단위·직접 복구/Studio 독립 배치는 선택 범위검증을완료했다. 실제새복사본11/12와Rill새CSV정답은testing기록을따른다. RXS12대화형모델오류진단·수정안은PARTIAL로유지한다. 다음RXS15–19에서기존갱신버전/작업수명/스키마영향을먼저재사용하고없는정정/중복계약만추가한다.

## RXS15 갱신 실행 계약

## RXS16 지속 갱신 작업 설계

기존 DuckDB worker와 메타데이터 DB를 유지하고 별도 큐 서버는 추가하지 않는다. 서버 파일 갱신에 request UUID·입력checksum/확장자·기준revision·actor/source를 묶은 지속 작업을 추가한다. 같은 요청/같은 입력은 같은 작업/영수증을 반환하고 다른 내용은409다. 입력은관리경로에별도보관하고worker에는복사본을전달해재시작후에도동일입력으로명시재시도할수있게한다. 클라이언트/일반조회에는경로/인증/SQL을반환하지않는다.

상태는queued/running/succeeded/failed/interrupted/cancelled다. 실제worker는한번씩DB CAS로실행권을받고짧은lease/heartbeat를유지한다. 서버재시작후만료된실행은interrupted로표시하며자동다시게시/다시적재하지않는다. 사용자가동일작업을명시재시도한다. 늦은이전worker는lease/state검사에서활성화를거절한다. source pointer의CAS와성공영수증을같은metadata transaction에서commit해commit직후응답유실도GET으로확인한다. 후보삭제전에는현재/보존버전참조를재확인하고DB결과가불명확하면삭제하지않는다.

API는기존동기파일교체를유지하면서새owner전용작업 admission/상태/최근작업/재시도를추가한다. 기존파일UI에는현재작업상태와동일요청확인/명시재시도를연결한다. 임의자동재실행·업무키upsert·원천API스케줄·운영다중서버전체보장을이번단계에섞지않는다. 소스별동시요청은기준revision/CAS로한번만활성화되며작업자권한을매전이확인한다. 취소의worker중단과큰데이터성능은RXS19에서확장한다.

최소검사:실SQLite+worker의정상/동일요청/다른payload/actor/원자rollback·직후유실/lease만료·소스변경거절·기존성공데이터보존. 실제브라우저에서admission응답유실GET복구·실제서버재시작후같은job재시도·새ID/중복버전0·게시불변·모바일/키보드까지확인한다. 부분검사만으로RXS16PASS로올리지않는다.

## RXS17 열 변경 영향·명시 복구

P2 지표/차원과 P5 재사용 계약에 연결한다. 기존 파일 교체의 엄격한 스키마 거절은 유지한다. 실패한 같은 갱신 작업/기준 파일 revision의 소유자만 현재 저장 분석의 블록·지표 의존 열을 읽어 영향 목록을 확인한다. FORMULA는 고정 피연산자의 실제 열을 사용하고, SQL 블록은 기존 제한 parser로 열을 추출한다. 파싱 실패/잘린 diff는 직접 확인 필요이며 영향 없음으로 단정하지 않는다. 저장 공통 필터/기간 열도 포함한다. 지표/블록 제목과 열 이름만 응답하고 SQL/원본 행/파일 경로를 반환하지 않는다.

원본 성공 데이터/정의/게시를 보존하고, 새 파일을 별도 소스로 업로드→기존 복제 화면에서 모든 열 명시 연결→전체 미리보기→비공개 새 복사본 저장/reload로 복구한다. 타입을 자동 변환하거나 영향을 받은 블록을 자동 제외하지 않는다. 미저장 초안/일반 레거시 위젯/Pivot/타 사용자 저장본은 이 조회 범위에 포함하지 않음을 화면에 명시한다. 삭제와 타입 변경 두 거절, FORMULA/차원/공통 기간 의존, 모르는 SQL·버전409·권한, 새 데이터의 독립 수치/Rill·모바일/키보드를 확인한 범위만 PASS다.

## RXS18 업무 키·수정 시점 정정 배치

P2의 믿을 수 있는 소스와 P3 저장 분석의 수치 일관성에 연결한다. 기존 전체 파일 교체는 그대로 두고, 파일 갱신의 선택 고급 설정에서 **단일 업무 키와 수정 시점 열**을 명시한 정정만 추가한다. 같은 actor/request/입력/기준 revision에 operation·열 설정도 묶는다. 지표·블록·게시를 다시 만들지 않고 기존 source pointer 활성화/성공 영수증 transaction과 지속 worker를 재사용한다.

기존 소스의 키는 유일·비어 있지 않아야 한다. 키는 문자열/정수 계열, 수정 시점은 날짜/타임스탬프 계열이며 기존/입력 스키마는 정확히 같아야 한다. 입력의 완전히 동일한 행은 중복 제거하고 같은 키의 최신 수정 시점을 선택한다. 같은 키·같은 수정 시점에 다른 내용은 모호하므로 전체 배치를 거절한다. 기존보다 늦은 수정만 반영하고 오래된 것은 무시하며 새 키는 추가한다. 같은 수정 시점의 다른 내용은 기존 데이터와 비교해도 거절한다. NULL 키/시점·중복 기존 키·잘못된 타입도 거절하며 자동 변환하지 않는다.

작업은 읽기 전용 기존 DuckDB를 새 후보에 ATTACH하고 후보만 수정한다. [공식 ATTACH 문서](https://duckdb.org/docs/current/sql/statements/attach.html)의 단일 쓰기 DB transaction 규칙을 따른다. 클라이언트 SQL/경로는 받지 않는다. 완전 중복/오래된 배치의 재수신은 성공 영수증만 확정하고 새 파일 버전을 만들지 않는다. 수정 시점만 최신이면 워터마크 보존을 위해 반영한다. 신규/수정/동일/오래됨/입력 중복·배치 내 이전 수정 건수를 구분한다. 삭제/tombstone·부분 열 patch·복합 키·원천 스케줄은 후속이며 이번 선택 범위로 일반화하지 않는다.

샘플은 주문3건→지연 환불 수정1건+신규 주문1건+오래된 수정/중복/동일 행을 가진 배치다. 정답은 최종4건/매출1000/환불90/순매출910 USD·금액 환불률9%다. 원본 업무일은 과거로 유지하고 수정 시점·업로드 시각과 구분한다. 동일/순서만 바뀐 배치 재수신·모호한 충돌 거절·새 서버 재시도에도 중복0, 기존 대시보드 reload·Rill 같은 최종4행·세폭/키보드까지 확인한다. 먼저 worker의 순수 업무 규칙을 실제 DuckDB로 검증하고 지속 작업/화면을 순서대로 연결한다.

## RXS19 대표 부하·취소 실행 계약

RXS16의 실제100만행 저장·재시작·Rill/Decimal 정답은 재사용한다. 기존 단일 worker의512MB 메모리/2GB spill·업로드/결과/대기열/시간/후보 저장 제한을 유지하고, 지속 갱신의 명시 취소가 **해당 실행의 큐 작업 제거 또는 물리 worker 중단**으로 이어지게 한다. 다른 요청을 취소하거나 성공 파일을 삭제하지 않는다. 취소 DB 상태를 먼저 확정하고 실행 문맥의 AbortSignal을 worker 제출에 전파한다. 다른 서버의 취소/lease 상실은 heartbeat에서 탐지하며 즉시 전역 중단을 주장하지 않는다. UI는 취소 완료와 정리 중을 구분하고 완료된 취소는 재활성화하지 않는다.

실제 대용량 배치에서 실행 중 Enter 취소→후보/보관 입력 정리→이전 버전·게시·숫자 보존→다음 정상 조회를 확인한다. 독립 큐 요청 보존·이미 취소된 문맥·늦은 응답·다른 서비스 인스턴스 취소/lease 상실은 하위 회귀로 검사한다. 시간·프로세스 RSS와 적용 제한은 실제 관측값으로 기록하며 단일 로컬 실행을 운영p95나 엄격한 프로세스 전체 메모리 한도로 부르지 않는다. crash 후 참조 불명 파일의 무조건 삭제·전역 저장량/다중 서버 admission·운영 부하·실기기는 별도다.

## RXS07/08 관계와 fact grain

P2 데이터/지표와 P5 재사용에 연결한다. 사용자 소유 DuckDB 파일 두 개의 **fact N: lookup1** 관계를 명시하고 비공개 독립 스냅샷을 생성한다. Git 변경 파일은fact·커밋 작성자 사전은lookup, 지출은fact·제공자 사전은lookup이다. source ID/정확한 revision·동일 타입의 키·추가할 범주 이름만 받고 사용자 SQL/경로는 받지 않는다. 키를 trim/cast/대소문자 변경하지 않으며 같은 원시 동등성으로 유일성을 검사한다. lookup중복/NULL/빈키는 거절하고, fact미매칭은 수/누락 속성을 보여준 뒤 명시 동의 시 행을 유지한다. LEFT JOIN 전후 fact행 수가 같지 않으면 저장하지 않는다. 부모 숫자는 범주 문자열로만 추가해 중복 합산 가능한 지표로 조용히 복사하지 않는다.

파일 경로는순수 문자열 함수로 basename/전체 부모 디렉터리/확장자를 추가한다. 같은 basename이 다른 경로에 존재하는 fixture에서 전체경로 distinct와basename distinct·COUNT(DISTINCT commit_id)·변경줄 합계를 구분한다. 파일이 없는 lookup커밋을 활동 커밋으로 세지 않는다. 의료형 fixture는지출 금액 보존·중복 제공자 키 거절/수정·미매칭 유지와 집계된 고유인원 수의 비가산 경고를 검증한다. 전체 고유인원은원본 person key 없이는 계산하지 않는다.

미리보기는 임시 worker파일에서품질·첫5행만 반환하고 metadata쓰기0/후보정리다. 저장은같은spec/두source revision/quality digest 재확인→원자source권한/revision검사+새비공개Database+actor/request영수증이다. 재시도는 같은 source를 반환하고 다른payload는409다. commit결과불명에서후보의참조를확인하기전삭제하지않는다. 새연결소스는고정스냅샷이며원본의자동갱신/파일교체/복원을허용하지않고명시재생성을안내한다.

비가산 열은profile/서버compiler/AI재구성profile에보존한다. structured metric의주값/분모/가중치/FORMULAleaf에서위반을거절하고AI SQL preview/save도서버근거검사없이실행하지않는다. 경고문만추가해SUM(고유인원)을허용하지않는다. 범용 소유 SQL은전문가경로로구분하며기업열보안전체완료를주장하지않는다. 실제샘플파일선택/품질오류→수정→미리보기/비공개저장→실제Luna생성/저장/reload·Rill동일CSV/390·768·1440·키보드를확인전두행은NOT_RUN이다.

## RXS12 대화형 열 오류 진단 후속

열 구성 거절은 이미 마지막 성공 파일을 보존한다. 새 진단은 같은 실패 job/기준 revision·소유 원본/대체 소스의 **열 이름·타입과 저장 의존성만** 읽고, 실제 gpt-6-luna가 원인 설명/명시 연결 수정안을 제안한다. SQL·원본 값·경로·토큰을 보내지 않는다. 제안은 존재하는 열/같은 타입·유일 원본 열/전체 의존 열 coverage로 서버 검증하며 누락·모호함은 미해결로 남긴다. 진단 중 기준 변경은409, 모델 실패는 기존 성공본/사용자 질문을 보존한다. 제안만으로 저장/파일 변경/블록 삭제를 실행하지 않는다.

사용자는 대체 소스를 고르고 질문→진단 제안 확인→기존 새 데이터 복사 화면에서 열을 직접 연결/단위 확인→전체 미리보기→비공개 복사본 저장/reload한다. 대화 설명을 복구 성공으로 세지 않으며 실제 새 정답·원본/게시/비대상 불변·세폭/키보드까지 수행한 뒤 해당 범위만 PASS로 올린다. 자유형 SQL 자동수정/원본 덮어쓰기·모든 소스 오류/기업정책 완료는 이번 계약이 아니다.

## RXS21–23 조직·그룹·행/열·AI 정책 구현 계약

다음 부족점은 일반 소유권과 조직 정책이 다르다는 점이다. 초기 계약은 **기존 저장 Dashboard의 조직 구성원용 읽기 화면**이다. 별도 Artifact ID/계산 엔진을 만들거나 기존 소유자 권한을 확장하지 않는다. 관리자만 소유 분석을 조직에 연결하고 그룹별 허용 블록/열·필수 행 범위·AI/export 허용을 명시한다. 일반 소유자 Studio/소스/SQL/AI/export API를 구성원에게 우회 개방하지 않는다. 비소유자는 기존 서버 소유권 검사로 거절되고, 조직 읽기 API가 유일한 새 접근 경로다. 읽기 전용 역할을 편집 역할이라고 표시하지 않는다.

조직/구성원(admin/viewer)·그룹·분석 정책을 metadata에 저장한다. actor는 JWT에서만 읽고 body의 사용자/회사/역할을 권한으로 신뢰하지 않는다. 구성원은 정확히 지정한 그룹 정책을 적용받으며 정책이 없으면 deny다. 읽기 요청마다 구성원 active/조직/분석 소유권·저장 revision/source 고정 파일을 검사하고, 지연 query/LLM 뒤 재확인한다. 회수 후 다음 API와 화면 재검사에서 캐시를 버리며 이미 받은 파일까지 회수한다고 약속하지 않는다. 사용자에게 다른 그룹 목록/원본 sourceId/SQL/정의/정책의 숨긴 행 값·숨긴 열 이름을 반환하지 않는다.

관리자가 선택한 블록은 서버의 저장 canonical 지표/차원 링크와 SQL 일치가 증명되어야 한다. 정의/FORMULA leaf/차원/공통 필터/기간 의존 열 모두가 허용 열에 포함돼야 하며 모르는 SQL/숨긴 열 의존 블록은 정책 등록부터 차단한다. 정책 필수 행 조건을 bound parameter로 **집계 전** 적용하고 사용자 필터는 허용 차원에서 AND로만 좁힌다. 후보 값/집계/상세/CSV/AI 모두 같은 compiler/권한 문맥을 쓴다. 숨긴 열로 필터/정렬/계산/원본 조회를 요청하면400/403이고 프런트에서만 숨기지 않는다. 페이지/결과/CSV 한도를 적용하고 쿼리 오류는 숨긴 스키마/경로를 반환하지 않는다.

AI는 조직+그룹의 명시 허용을 확인한 후 허용 블록·분류 이름만 받아 조회 계획을 제안한다. 임의 SQL/도구/다른 source를 받지 않고 모델 blockId/필터를 같은 정책에서 다시 검증한다. 실제 숫자는 서버가 계산하며 모델 텍스트로 근거 없는 금액/인원을 만들지 않는다. allowAi=false는 제공자 호출 전에 차단한다. 역할/정책/회수·쿼리/AI/export 결과의 감사에는 actor/org/policy/version/대상/결과만 남기고 raw값/질문/비밀을 기록하지 않는다.

VM 고정 마진18행에 관리자/파트너A/B 세 로컬 테스트 계정을 적용한다. 같은 분석 ID의 A/B 회사 행 정답을 독립 CSV로 계산한다. 숨긴 원가/고객명과 타 그룹 값이 profile/값후보/집계/상세/CSV/AI 문맥/오류/회수 후 결과에 없는지 sentinel로 실제 검사한다. 사용자 filter 제거/다른 그룹·source·block ID/hidden column 조작·정책 revision 경합을 검증한다. 모바일/키보드/디자인과 실제 Luna를 확인 전 RXS21–23은 NOT_RUN이다. 조직 편집/SSO/SCIM·다른 독립 Artifact의 전역 회수·실운영/실기기는 별도이며 이 읽기 경계를 모든 기업 정책 완료로 과장하지 않는다.

정책 경계 검토 후: 초기 구성원 결과/AI 캐시는 사용하지 않으며 HTTP `Cache-Control:no-store`를 적용한다. DB와 브라우저의 과거 다른 그룹 결과를 재활용하지 않는다. CSV/AI/JSON은 한도 안에서 전부 버퍼링하고 동일 권한·정책·파일/분석 버전을 최종 재확인한 뒤에만 응답한다. provider 토큰이나 CSV행을 검사 전에 스트리밍하지 않는다. A→B 연속 조회/권한 회수 중 대기 응답을 sentinel로 확인한다.

## RXS20 조건 보고·앱 안 알림 계약

외부 메일/Slack·유료 스케줄러는 추가하지 않는다. 조직 보기의 로그인 구성원이 **본인만 수신하는 앱 안 보고/알림**을 예약한다. 저장된 정책의 숫자 KPI 한 개에 `초과/미만`, 임계값과 최소60초 주기를 설정한다. 원본/SQL/숨긴 열·다른 수신자를 입력받지 않는다. 서버 DB의 지속 작업 + occurrence별 unique 영수증 + lease CAS로 다중 실행/재시작의 중복 보고를 막는다. 작업은 최신 성공 쿼리를 새로 실행하고 중앙 행/열 정책과 최종 버전을 재확인한 결과만 저장한다. 실패/정책변경/소스변경 시 과거 숫자로 경보하지 않는다. 권한 회수/만료 뒤 보고 목록·이전 기록도 현재 권한을 재검사하고 숫자를 숨긴다. 조건 불일치도 실행 이력으로 남기되 알림이라고 표시하지 않는다. 정시 실시간 전달·외부 채널 exactly-once·운영 분산 스케줄러는 별도다.

A20 Given 조직별 실제 샘플/독립 매출 정답, When 임계값을 저장하고 최초 예약을 실행/중복 재시도/서버 재시작, Then 같은 발생 시점의 기록 한 건·정확한 값/조건 안내, 미달/실패/회수에는 알림0. 실제 모바일/키보드와 DB 영수증을 확인한다.

## RXS24 인증된 동일 origin 포털 임베드 계약

우선 VM과 같은 origin의 데모 포털에서 조직 보기 화면을 iframe으로 사용한다. 브라우저 로그인 JWT가 실제 요청 identity이며 URL/body에 사용자·그룹을 넣어 가장하지 않는다. 별도 익명 토큰/공유 URL은 사용하지 않는다. 부모는 검증된 테마(light/dark)와 허용된 사용자 필터만 URL 상태로 전달한다. 프레임은 중앙 정책을 새로 조회한 후 사용자 필터를 좁히는 데만 적용한다. 원본 행 범위·허용 열/블록·AI/CSV 정책은 프레임에서도 동일하다. 질문/AI 결과는 해당 프레임·정책 revision·로그인 세션 메모리에만 있고, 계정/경로/필터 scope 변경에는 요청 취소·숫자/질문 정리를 한다. 정책 만료/권한 회수·익명 접근은 재조회 시 차단한다. 타 origin 호스트 JWT 교환·SSO/서명 embed 토큰·외부 호스트 postMessage API는 범위 밖이며 해당 기능을 구현했다고 주장하지 않는다.

A24 Given A/B 로컬 포털 로그인, When 포털의 테마/필터를 적용하고 프레임에서 실제 Luna 질문/계정 전환/정책 만료, Then 같은 독립 정답·필터 상태, A 질문/숫자가 B에0, 만료 뒤 데이터0, 390/768/1440 넘침0·키보드로 테마/필터/질문 조작. 외부 배포/클라우드 실사용으로 승격하지 않는다.

보고 계약 보완: 작업과 발생 기록은 실행 viewRevision에 고정한다. 현재 revision이 다르면 과거 숫자를 숨기고 새 예약으로 재확인한다. 최대 활성10개/구성원·한 tick20개·중단 기간은 최신 발생1건만 따라잡는다. 고유 키는 (reportId, scheduledAt)이며 receipt·다음 실행 시점 저장을 현재 lease token/활성/config version에 대한 CAS와 한 transaction으로 묶는다. 보고는 집계 CSV 보관 허용 정책도 요구한다. 임베드는 신뢰된 같은 origin 부모만 지원하고 실제 문서 응답의 frame-ancestors self를 검증하며, 응답 적용/다운로드 직전 로그인 세대·뷰/필터 scope를 확인한다.
