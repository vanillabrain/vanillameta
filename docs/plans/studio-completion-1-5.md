# Studio 잔여 1–5 실행 계획

Status: Draft. 기준 develop-v2 5679f5f0. P3/P4/P5·FR008/009/011·TC005/TC032. 사용자 요청: 저장 복구, 대화 연결, Studio 통합, 커머스 업무 검증, 출시 검증을 순차 진행한다.

## 계약과 종료 조건

1. UC032의 기존 영수증 확인을 먼저 실행한다. 서버 직렬 저장 경계에서 영수증이 없고 제안이 사라졌음을 확정하는 구조화 오류에만 명시 재제안 전환을 허용한다. 통신/5xx/권한/기타400/409에는 허용하지 않는다. 질문·소스를 유지하며 새 AI/저장을 자동 실행하지 않는다. 새 미리보기를 검토한 뒤 새 requestId로 저장한다. 캐시 만료와 서버 재시작은 같은 제안 부재 경계이나 실제 실행 근거는 각각 구분한다.
2. 편집기 대화의 업무 의미 질문도 원 제안으로 이어가는 링크를 제공한다. 권한 확인된 제안 캐시에 원 질문을 함께 반환하고 생성 화면은 그 질문을 복원한다. 기존 분모 선택→동일 질문/답변 재제안 경로를 재사용한다. 모든 임의 자연어 답변 자동 처리로 확대하지 않는다.
3. Ego 하나에서 편집기 대화→생성안 이어 열기→분모 답변→미리보기→저장→게시→새로고침→복제를 확인한다. 원본 보존·권한·요청 중복 방지와390/768/1440을 함께 확인한다. 공개 게시가 필요하면 공개 합성 데이터만 사용하고 검증 후 해당 링크만 중지한다.
4. 고객 비식별 데이터가 제공되기 전에는 저장소의 공개 합성 커머스 샘플로 검증한다. Decimal 독립 정답과 매출/환불/순매출/금액 기준 환불률을 비교하고 고객 업무 수용과 구분한다. 고객 데이터 경로는 비동기로 요청했다.
5. 통합 단위·빌드/type/lint·격리 core8·접근 가능한 로컬 재시작/동시 요청을 실행한다. 운영 MySQL·실휴대폰·VoiceOver는 실제 접근/실행 증거 없이 PASS로 기록하지 않는다. 기존 strict 오류는 자동 기준선 수용 없이 기록한다.

## 변경 범위

- studio-creation.service: 영수증 우선 순서 보존·구조화 제안 부재 오류·캐시 원 질문.
- StudioCreate/StudioConversationCreation: 복구 재제안과 의미 확인 handoff. 기존 토큰/컴포넌트만 사용.
- 관련 회귀, UC032/TC032·Studio 증빙/AGENTS 동기화. DB 스키마·의존성·모델 변경 없음.

## 검증·검토

각 경계의 실패 회귀를 먼저 추가하고 최소 구현 후 관련 FE/BE→Ego→통합 검사한다. Main이 작성 후 명세 대조하며 독립 점검은 제공자400으로 실행되지 않았다. 독립 리뷰/사람 수용을 주장하지 않는다. 실행 로그/캡처는 /tmp/vm-completion-1-5 에 보관한다. 통과 범위와 미실행 조건을 분리한 뒤 현재 브랜치 commit/push한다.

실행 중 관찰: 금액 분모 답변 후 모델이 실제 존재하는 refund_amount/revenue의 매핑을 다시 물었다. 최초 실패를 보존하고 기존 분모 계약을 명확히 한 지시로 재검증한다. 수동 SQL 대체나 모델 자동 변경은 없다.

추가 관찰/설계: 수정+명시저장 뒤 보존/게시금지 문장이 이어지면 저장을 놓쳤다. 저장 금지의 우선권과 게시 동의 경계를 유지하고, 따옴표 밖의 문장별 명시 저장 명령만 판별한다. 인용문 안 예시는 저장 동의가 아니며 새로운 자연어 범용 planner는 도입하지 않는다. 실행 서비스 회귀 후 Ego 같은 복제본에서 재검증한다.
