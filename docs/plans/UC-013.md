# UC-013 구현 계획

P3 / FR009·010 / UC013 BR001~005. 관찰한 차이: 고객이 AI 변경 목적을 수동으로 골라야 하며 질문 하나의 내용/배치 판별이 없다. 기존 editor/compiler·AI·공통 이력·저장 경로를 재사용한다.

1. AIWF UC/설계/TC·use-case diagram을 작성하고 별도 대조·strict lint/pin. 기존 문서12개 오류는 분리한다.
2. 분류 엄격 응답·clarify·취소 테스트와 Bi editor auto dispatch/권한 우선 테스트를 실패 확인 후 구현한다.
3. FE 기본auto·고급 목적 접기·실제 목적 응답 검증/안내·clarify 보존 회귀를 구현한다.
4. 관련 BE/FE 테스트·build/type/변경lint. 기존 로컬 서버를 새 BE 빌드로 갱신하되 다른 프로젝트 포트는 종료하지 않는다.
5. Ego 검증 분석22에서 기본auto 내용→배치→모호 질문→이력/저장/reload·비대상 보존,390/1440 크기·정렬·접힌 설정을 확인한다. 실LLM과 API·UI 증거를 분리한다. 자동 분류가 목표를 충족하지 않으면 명시 모드로 바꿔 PASS 처리하지 않는다.
6. 문서·증빙·pin/packet·drumcap commit/push. 실제 휴대폰/운영MySQL·자동저장·게시·다중블록/전체P3 완료는 별도다.

실제 자동 내용 요청은 분류+생성 중 axios 기본10초 제한에 걸렸다(status0·약10002ms). editor AI 요청에만 기존 AiDashboardPanel과 동일한180000ms timeout을 적용한다. 같은 AbortSignal/세션 토큰·서버 취소를 유지하며 전체 API 기본 timeout은 변경하지 않는다. 설정 전달 회귀를 먼저 실패 확인 후 수정했다.
