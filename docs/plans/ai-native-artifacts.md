# 팀의 AI로 아티팩트를 다루는 VanillaMeta (설계 초안 2)

상태: 초안 2. architect 검토를 반영했다. 구현 전이며 아직 아무 코드도 바꾸지 않았다. 9절의 결정 14개를 모두 사용자가 정했다. 구현 전에 한 번 더 정할 세부는 9절 끝의 "남은 세부"에 있다.

초안 1에서 바로잡은 것: (1) 외부에서 만든 `StudioDocumentV1`을 Studio `save`로 저장할 수 있다는 가정은 틀렸다. 기존 블록의 계산 정의·참조를 바꾸면 거부된다. (2) 새 대시보드를 AI 없이 만드는 경로는 있다(레거시 `POST /ai/dashboard-save`). (3) 별도의 `can()` 함수 대신 이미 단일 관문인 `currentRights`를 확장한다. (4) 로컬 stdio가 로그인 JWT를 그대로 쓰는 점이 가장 큰 보안 누락이었다. (5) 소프트 삭제는 지금 없다. (6) 감사 테이블(`EnterpriseAuditEvent`)과 마지막 admin 보호는 이미 있다.

## 1. 목표

팀원이 자기 AI(MCP 또는 제공되는 skill을 쓰는 Claude Code, Codex 등)로 VanillaMeta의 아티팩트를 만들고 고치고 지울 수 있어야 한다. 서버가 제공하는 AI는 선택 기능이며, 설정하지 않아도 일반 사용과 MCP 모드로 모든 작업이 된다. 권한은 관리자만 부여하고 사용자는 허용된 범위 안에서만 쓴다.

요구사항 원문 (사용자 지시):

1. MCP나 제공되는 skill로 팀원이 본인의 AI를 활용해 VanillaMeta를 쓴다. 대상 아티팩트는 시각화·대시보드, 문서, 슬라이드, 엑셀, html, pdf 등이다.
2. 자체 제공 AI는 관리자 페이지에서 API 또는 OAuth 설정으로 쓸 수 있다.
3. 자체 AI를 설정하지 않으면 일반 사용 및 MCP 모드로 동작한다. 이 기능들은 사람이 하는 아티팩트 생성·수정·삭제다.
4. 구글 클라우드와 애저 클라우드 연계는 옵션이며 관리자 승인 하에 연다.
5. 관리자는 회원을 관리하고 등급별 권한을 부여할 수 있다.
6. 관리자 외에는 권한을 부여할 수 없고 허용된 권한 안에서만 쓸 수 있다.
7. (추가 지시 2026-11-05) 아티팩트는 우리가 제공하는 서버 AI가 아니라 MCP를 통해 생성·저장·수정·삭제하며, 본인의 작업물은 언제든 할 수 있어야 한다.

변하지 않는 제약: AI 모델 설정은 `gpt-6-luna`를 유지하고 다른 모델이나 로컬 LLM으로 자동 대체하지 않는다. VoiceOver 검증은 기존 차단 상태를 유지한다.

## 3. 설계 원칙

1. **하나의 검증·저장 커널.** 사람(UI), 외부 AI(MCP, skill), 서버 AI가 같은 명령 경로를 지난다. 서버 AI는 그 앞의 선택적 "제안 생성기"일 뿐이다. 서버 AI가 없어도 아티팩트 작업이 막히지 않는다(요구 1, 3).
2. **AI는 사용자보다 센 권한을 가질 수 없다.** 외부 AI의 유효 권한은 사용자 권한과 사용자가 승인한 scope의 교집합이다(요구 6). 이를 지키려면 외부 AI가 사용자의 로그인 JWT를 직접 쥐지 않아야 한다.
3. **본인 작업물은 언제든 쓴다.** 소유자는 서버 AI 없이 MCP로 자기 아티팩트를 생성·저장·수정·삭제할 수 있다(사용자 지시 2026-11-05). 새로 만든 대시보드는 소유자만 보고 게시는 별도 스냅샷이다. 이미 공유·게시한 것을 고치는 일도 막지 않고, 대신 이전 버전 복원으로 실수를 되돌릴 수 있게 한다(4.1).
4. **서버 강제.** `confirmWrite: true`는 AI가 채우는 입력이라 사람 승인의 증거가 아니다(검증 후 버려지는 값). 승인은 서버가 상태·scope·쿼터로 강제한다.
5. **기존 것을 먼저 쓴다.** 새 함수·테이블은 기존 구조로 안 되는 것에만 만든다.

## 4. 구조

### 4.1 아티팩트 쓰기 경로

단계: `describe → validate/preview → save(create | update) → [비공개] → publish/share → delete → export`.

- **생성 입력은 기존 의미 블록으로 한다.** `title`, `kind`, `metric{id, definitionVersion}` 또는 `FORMULA`, `dimension`, `presentation`이다. 검증은 이미 AI 없이 동작하는 `validateBlock → compile → preview`(`studio-creation.service.ts:856,1059`)를 재사용한다. 초안 1의 "`StudioDocumentV1`을 외부에서 받아 저장"은 현재 `save`가 거부하므로 채택하지 않는다.
- **새 `create`는 메모리 제안 저장소에 의존하지 않는다.** 현재 제안은 프로세스 메모리(64개, 약 10분)에 있어 재시작·다중 인스턴스에서 사라진다(`studio-creation.service.ts:110`).
- **기존 대시보드에 차트 추가·지표 변경은 새 작업이다.** 지금 `save`가 막는다. 외부 AI가 지표 식(`FORMULA`)을 정의하게 할지는 9절 결정이다.
- **쓰기 범위는 소유한 것만이다.** MCP 쓰기(생성·저장·수정·삭제)는 actor가 소유자인 아티팩트에만 한다. 편집 grant를 받은 남의 아티팩트는 MCP로 고치지 못한다(사용자 결정). 소유자의 수정은 공유·게시된 것도 허용한다. 받은 사람에게 즉시 보이므로 **이전 버전 복원**을 제공한다. 보고서는 이미 버전이 있다. 대시보드는 지금 해시 revision뿐이라 저장 이력과 복원은 새 설계 항목이다(사용자 결정).
- **delete.** 화면 삭제와 동일하게 한다(사용자 결정). 공유·게시·전달·댓글 등 의존성이 0일 때만 삭제되고 "영향 확인 → 삭제" 2단계를 재사용한다. 의존성 때문에 거절되면 이유(어떤 공유·게시가 걸려 있는지)를 오류에 담아 돌려준다. MCP에서 공유·게시를 해제하는 도구가 필요한지는 1b 구현 때 확인한다. 소프트 삭제와 복구 기간은 이번 범위에 넣지 않는다.
- 모든 쓰기는 `expectedRevision`(낙관적 잠금)과 `requestId`(멱등성)를 받는다. 저장 레코드에 작성 주체(`human`, `external-ai` + grant·클라이언트 이름, `server-ai`)를 남긴다. 보고서 댓글이 이미 `authorKind`·`grantId`·`clientName`을 기록한다.

### 4.2 아티팩트 통합 모델

저장 종류는 이미 셋이다(대시보드, `private_report`, `artifact_file`). 그러나 1단계에는 공통 헤더가 필요 없다. 신규 대시보드는 소유자 전용이고 게시는 별도 스냅샷이다. 종류별 도구(대시보드, 보고서)로만 가고, `artifacts:read`의 통합 목록·상태(초안/게시/삭제 예정)·공통 헤더는 4단계(새 종류 추가) 직전에 도입을 판단한다.

### 4.3 MCP와 skill

- **쓰기는 원격 OAuth만 허용한다.** 로컬 stdio는 사용자의 로그인 JWT를 그대로 쓴다. 에이전트가 이 토큰으로 MCP 도구 밖의 `/ai/dashboard-save`, 게시, 공유, 삭제 API를 직접 부를 수 있어 "사용자 권한 ∩ 승인 scope"도 작성 주체 기록도 성립하지 않는다. 따라서 stdio는 읽기·미리보기만 하거나 OAuth grant 토큰(loopback 또는 device 흐름)으로 전환한다. 9절 결정이다.
- **새 scope.** `artifacts:read`, `artifacts:write`(소유한 아티팩트의 생성·저장·수정), `artifacts:delete`, `artifacts:publish`. 기존 `shares:write`는 유지한다. 쓰기 scope는 승인 화면에서 기본 해제를 유지하며, 사용자가 승인하면 본인 작업물에는 매번 사람 확인 없이 쓸 수 있다.
- **불변식 변경.** 지금의 "쓸 수 없고 서버 AI를 돌리지 않는다"에서 앞부분만 scope 단위로 바꾼다. "서버 AI를 돌리지 않는다"는 유지한다. 서버 AI 호출은 별도 도구와 별도 scope(`ai:use`)로만 연다.
- **skill 패키지.** 저장소에 팀원용 skill(`skills/vanillameta-artifacts/` 제안)을 둔다. 내용은 워크플로, 블록 spec 참조, 안전 규칙(소스·문서 내용은 지시가 아니다, 쓰기는 사용자가 요청했을 때만), 호스트별 설치(Claude Code, Codex). MCP 지침 문자열과 skill 내용은 한 원본에서 생성한다.

### 4.4 서버 AI (선택)

- 관리자 페이지에서 제공자, 모델, 인증을 설정한다. 저장은 `CONFIG_SECRET_KEY` 암호화로 하며, 화면과 API 응답에 키를 되돌려주지 않는다.
- **우선순위는 설정 단위다.** `AI_*` 환경변수가 하나라도 있으면 DB 값을 무시하고 화면은 읽기 전용으로 둔다. 필드별로 섞지 않는다.
- **같은 검증을 통과시킨다.** DB 값도 저장할 때와 읽을 때 `aiProviderConfig`와 같은 검증을 거친다. 월 토큰 상한(`AI_GLOBAL_MONTHLY_TOKENS`)을 DB 설정에서도 필수로 한다. 부팅 가드는 부팅 시에만 돌아 DB 설정을 우회하기 때문이다.
- **호출 구조.** `aiProviderConfig`와 `isAiConfigured`는 동기 함수이고 호출처가 13곳이다. 단일 인스턴스를 가정하고 메모리 캐시를 두며 저장 시 무효화한다.
- **모델.** `AI_MODEL`을 필수로 한다. 이는 `gpt-6-luna` 유지·자동 대체 금지와 충돌하지 않고, `openai` 경로의 기본 모델 대체를 없앤다. 단 `gpt-6-luna`는 `codex` 전용 상수이고 `prod`는 `codex`를 금지하므로, 운영에서 이 모델을 쓰는 길은 `openai`·`openai-compatible` + 명시한 `AI_MODEL`뿐이다.
- **키 회전.** `enc:v1`과 `doc:v1`은 포맷 버전이지 키 버전이 아니다. AI 키는 (설정 ID + 용도)를 AAD로 묶어 봉인한다. 회전까지 하려면 키 링(현재·이전 키, 키 ID)과 재암호화 작업이 필요하다. 범위 밖으로 두면 "`CONFIG_SECRET_KEY`를 바꾸면 저장된 모든 비밀이 무효가 된다"고 문서에 명시한다.
- **미설정 모드.** 서버 AI 버튼은 숨기거나 안내와 함께 비활성화한다(`GET /ai/status`). 나머지 기능은 영향이 없다. 이를 위해 지금 서버 AI 게이트를 타는 Studio 신규 생성·차트 수정에 AI 없는 사람용 경로가 필요한지 검토한다(요구 3).
- **OAuth.** 저장소에는 제공자 OAuth가 없다. 사용자 결정(2026-11-05): 1차는 API 키 방식만 구현하고 제공자 OAuth는 뒤로 미룬다. 다시 필요해지면 `prod`의 `codex` 금지와 약관 확인부터 한다.

### 4.5 클라우드 연계 (옵션, 관리자 승인)

- 제공자별 정책 상태: `disabled`(기본), `requested`, `approved`, `revoked`. 승인한 관리자와 시각을 남긴다.
- 기존 provider의 `configured()`는 "환경변수 구성됨 AND 정책 approved"일 때만 참이 된다. 사용자는 요청하고 관리자가 승인한다.
- Azure 범위는 사용자 결정(2026-11-05)으로 "Microsoft 문서"(Word/Excel/OneDrive)다. 기존 Microsoft Docs provider를 확장하고 이 승인 게이트를 적용한다. Azure 데이터 소스와 Azure OpenAI는 이번 범위가 아니다.

### 4.6 회원·등급·권한

- **새 `can()` 함수를 만들지 않는다.** 이미 단일 관문인 `currentRights`와 `SourceAccessService`의 소유자 분기 안에서 "등급 능력과의 교집합"을 계산한다. 새 경로에만 새 함수를 붙이면 UI의 게시·공유·내보내기가 등급을 계속 무시하고 권한 모델이 세 번째로 늘기 때문이다.
- **진입점 전수 검사.** 같은 검사를 소스 생성, `prepareSave` 신규, 보고서 capture 저장, 파일 업로드, 게시, 거버넌스 정책 변경에도 건다.
- **등급(결정됨).** 4단계다. `admin`(관리), `editor`(본인 아티팩트 생성·수정·삭제·게시), `contributor`(생성·수정 초안만, 게시 불가), `viewer`(읽기). 등급은 능력 묶음에 대응한다. 역할 enum 확장(현재 `admin|member`)이 필요하다. 조직 admin이 등급 기본값을 능력 단위로 덮어쓸 수 있다.
- **등급과 소유자 권한의 합성(결정됨).** 다른 사람에게 편집·게시 같은 권한을 주는 일은 admin만 한다. `editor` 이하는 본인 아티팩트를 만들고 고치고 지우며, 읽기 공유는 할 수 있다. 소유자 무조건 전권(`currentRights:122-123`)은 등급 능력과의 교집합이 되도록 바꾼다. 지금의 "admin이면서 소유자만 권한 부여"는 "admin만"으로 단순화한다.
- **MCP 토큰의 유효 권한** = 사용자 능력 ∩ 승인 scope.
- **부여 권한.** 등급·능력 변경은 조직 admin만 한다(서버에서 강제, 감사 기록). 마지막 admin 보호는 이미 있다(본인 강등·비활성 차단).
- **조직 admin 허점(결정됨).** 조직 생성 경로 두 곳(enterprise, 거버넌스)이 열려 있고, 거버넌스 `setMember`는 본인 동의 코드가 없다. 인스턴스당 조직 하나로 하고 조직 생성은 부트스트랩 admin만 한다. 기존 다중 조직 데이터는 이행하지 않고 새 설치에만 적용한다(조직 생성만 막는다). `SIGNUP_MODE`는 `invite` 또는 `closed`를 권장 기본으로 한다.
- **미소속 사용자.** 조직이 없는 사용자는 자기 자원에 전권을 갖고 감사도 남지 않는다. 기본 등급과 감사 처리, 가입 → 조직 연결 흐름(접근 초대 코드와 enterprise 등록 코드는 별개 메커니즘)은 9절 "남은 세부"다.
- **관리자 페이지 `/admin`.** 회원(목록, 초대, 비활성, 등급·능력), 서버 AI 설정, 클라우드 연계 승인, 사용량·쿼터, 감사 로그. 지금 CLI로만 되는 초대 코드와 쿼터를 HTTP API와 화면으로 옮긴다.

### 4.7 감사

기존 `EnterpriseAuditEvent`를 재사용한다. 외부 AI·서버 AI 쓰기에는 작성 주체와 grant·클라이언트를 함께 기록한다. 권한·설정 변경도 같은 경로에 기록한다. 미소속 사용자의 작업을 기록할지는 4.6의 결정과 함께 정한다.

## 7. 단계

쓰기 scope가 권한 검사에 의존하므로 권한 작업을 먼저 한다. 각 단계는 독립 배포·검증한다.

1. **1a. 권한 기반.** 역할 enum 확장, 조직 생성 경로 2곳 차단, `currentRights`·소유자 분기에 등급 능력 교집합, 생성 진입점 검사.
2. **1b. 대시보드 쓰기.** 블록 spec 신규 생성(메모리 제안 저장소에 의존하지 않음), 원격 쓰기 scope, 작성 주체 기록, 소유자 한정 쓰기, 대시보드 저장 이력과 이전 버전 복원, stdio 인증 정리.
3. **1c. 보고서와 skill.** 보고서 MCP 쓰기, 팀원용 skill 첫 버전.
4. **2. 관리자 페이지.** 회원·등급·능력, 초대·쿼터 화면, 감사 로그 열람, 서버 AI 설정(API 키 방식).
5. **3. 클라우드 연계 게이트.** 정책 상태와 승인 흐름, 기존 provider 연결.
6. **4. 새 아티팩트 종류.** html, pdf(내보내기), 엑셀, 슬라이드를 하나씩. 이때 공통 헤더 도입을 판단.
7. **5. 후순위.** 서버 AI의 제공자 OAuth(1차에서 제외). Azure 데이터 소스·Azure OpenAI는 범위 밖이다. Microsoft 문서 연계는 3단계에 포함한다.

| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 서버 AI 없는 Docker 스택에서 Claude Code와 Codex가 원격 MCP로 대시보드·보고서를 생성·수정·삭제한다. 각 호스트의 실제 도구 이벤트와 Studio 재열기 확인                                                                                                                                                                               |

| 3    | 서버 AI 미설정에서 사람 UI와 MCP 모두 생성·수정·삭제가 된다. 사람 UI의 신규 생성·차트 수정이 서버 AI 없이 되는지 포함. AI 버튼은 안내와 함께 비활성                                                                                                                                                                                 |

## 9. 결정이 필요한 것

1. **[결정됨] 서버 AI의 "OAuth 설정".** 1차는 API 키 방식만 구현한다. 제공자 OAuth는 후순위이며 필요해지면 `prod`의 `codex` 금지와 구독 계정 공유 약관부터 확인한다. 모델은 `gpt-6-luna`를 유지한다.
2. **[결정됨] Azure 연계의 범위.** Microsoft 문서(Word/Excel/OneDrive). Azure 데이터 소스와 Azure OpenAI는 이번 범위가 아니다.
3. **[결정됨] 등급.** 4단계: `admin`/`editor`/`contributor`/`viewer`.
4. **[결정됨] 게시·공유.** MCP로 게시·공유는 별도 scope(`artifacts:publish`, `shares:write`)를 사용자가 승인했을 때만 허용한다. 기본은 해제다.
5. **[결정됨] 첫 구현 대상.** 대시보드와 보고서. 나머지 종류는 4단계에서 하나씩 추가한다.
6. **[결정됨] 다중 조직.** 인스턴스당 조직 하나. 조직 생성은 부트스트랩 admin만 한다.
7. **[결정됨] 로컬 stdio의 인증 모델.** 쓰기는 원격 OAuth만 허용한다. stdio는 읽기·미리보기로 제한한다.
8. **[결정됨] 등급과 소유자 권한.** 권한 부여는 admin만 한다. editor는 본인 것의 생성·수정·삭제와 읽기 공유만 한다.
9. **[결정됨] 기존 조직 이행.** 마이그레이션 없이 새 설치에만 적용한다. 기존 다중 조직 데이터는 그대로 두고 조직 생성만 막는다.
10. **[결정됨] 외부 AI의 지표 정의.** 1차는 이미 등록된 지표로만 블록을 만든다. `FORMULA` 정의와 기존 대시보드에 새 지표 추가는 사람이 한다. (질문 도구 선택지 이름의 "미등록"은 "등록된"의 오기였고 설명 기준으로 확정했다.)
11. **[결정됨] 문서 = 보고서.** 1차는 보고서를 문서 아티팩트로 본다. 독립 문서는 필요할 때 4단계에서 추가한다.
12. **[결정됨] MCP 삭제와 의존성.** 화면과 동일하게 의존성 0일 때만 삭제한다.
13. **[결정됨] 실수 되돌리기.** 이전 버전 복원을 제공한다.
14. **[결정됨] MCP 쓰기 범위.** 내가 소유한 아티팩트만.

## 10. 비목표

- 외부 AI가 임의 코드나 SQL을 서버에서 실행하는 기능.
- MCP를 통한 권한·회원 관리(관리자 기능은 웹 화면에서만).
- 공개 인터넷 노출용 보안 모델(체험용 Docker 스택은 신뢰하는 LAN 한정이다).
- 기존 테이블의 일괄 이행.

### 추가로 정한 세부 (2026-11-05)

- **부트스트랩 admin: 설정값으로 지정.** 환경변수(예: `BOOTSTRAP_ADMIN_USER_ID`)에 적은 로그인 ID만 첫 조직을 만들고 admin이 된다.
- **미소속 사용자: 조직 밖은 사용 불가.** 조직에 연결되기 전에는 아티팩트를 만들거나 MCP를 연결할 수 없고 대기 화면만 보인다.
- **가입 → 조직 연결: enterprise 등록 코드.** 직원이 발급한 코드를 admin이 입력해 조직에 추가한다(본인 동의 포함). 접근 초대 코드는 가입 허용 용도로만 남긴다.

### 구현 시 영향 (1a에서 반드시 처리)

- **Docker 체험 스택.** 시드 계정 `guest`(와 로컬 개발 `admin`)는 조직이 없다. "조직 밖은 사용 불가"를 적용하면 체험 스택의 첫 화면이 깨진다. 시드가 조직을 만들고 `guest`를 admin으로 연결하거나, compose가 `BOOTSTRAP_ADMIN_USER_ID=guest`를 넣어야 한다. `scripts/docker-smoke.sh`와 `README`의 로그인 안내도 함께 검증한다.
- **기존 사용자.** 조직 없이 자기 자원을 쓰던 사용자는 이행하지 않기로 했으므로(결정 9) 새 설치에만 이 규칙을 적용한다. 기존 설치는 기능 플래그로 구분한다.
