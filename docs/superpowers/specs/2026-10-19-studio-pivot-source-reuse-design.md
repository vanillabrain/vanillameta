# Studio 집계 Pivot의 소유자 소스 교체 복제

상태: 설계 검토 대기. 2026-10-19 사용자의 `다음`은 앞서 제시한 범위의 상세 설계 진행 승인이다. 이 문서는 아직 구현·실행 검증 승인이 아니며 제품 기능 완료를 뜻하지 않는다.

기준: `cb442029556bd90b2094b3d5c93c0217a2f64294`, develop-v2. P5/FR-012, UC020/UC024 및 [Studio Pivot 계획](../../plans/studio-pivot.md)의 다른 소스 매핑 후속이다. 기존 [SP01~07 증빙](../../testing/studio-pivot.md)은 관련 변경이 없는 조건만 재사용한다.

## 1. 목적과 성공 기준

사용자는 저장된 차트·집계 Pivot 혼합 대시보드를 본인의 다른 파일 소스에 연결하고, 실제 대상 데이터의 전체 결과를 확인한 뒤 새 비공개 대시보드로 저장한다. 원본 수정이나 계산식 수동 재작성 없이 같은 분석을 재사용하는 것이 목적이다.

성공은 다음을 모두 충족하는 선택 흐름이다.

- 원본의 마지막 저장본을 읽고 사용 열·지표·조건과 영향 블록을 설명한다. Studio의 미저장 초안은 포함하지 않는다.
- 명시적으로 연결한 대상 열에서 차트와 Pivot을 계산한다. 미리보기 때문에 Metric/PersonalView/Dashboard/Widget/StudioState/영수증 행을 생성·변경하지 않는다.
- 저장 한 번에 필요한 새 지표 그래프와 혼합 대시보드를 확정한다. 원본 지표·개인 보기·배치·게시·공유 및 대상의 기존 지표를 덮어쓰지 않는다.
- 복사본은 새 dashboard/block ID, 원래 순서와 xs/md/lg 좌표·크기, 표시 형식을 보존하고 대상 소스만 참조한다. 새 게시·익명 링크·grant는 만들지 않는다.
- 잘못된 연결·지원하지 않는 의미·기준 변경은 보존형 오류로 끝난다. Pivot을 누락한 성공이나 더 넓은 기간·필터의 성공을 반환하지 않는다.

## 2. 범위와 선택한 접근

기존 `GET /bi/dashboards/:id/reuse`, `POST .../reuse/preview`, `POST .../reuse`와 `/dashboard/:id/reuse?editor=studio`를 확장한다. 새 복제 서비스·DB 테이블·외부 큐·분석 엔진·UI 프레임워크는 추가하지 않는다.

| 대안 | 장점 | 부담과 판단 |
| --- | --- | --- |
| 기존 복제 경로 + 검증한 임시 지표로 읽기 계산 | 기존 열 연결·ticket·영수증·원자 저장을 재사용하며 미리보기 쓰기0 | 혼합 블록 모델과 집계 계산 준비 단계 분리가 필요하다. 채택한다. |
| 대상의 이미 저장된 지표만 사용자가 수동 선택 | 지표 생성 변경이 적다 | 사용자가 같은 계산식을 먼저 만들어야 하며 이름이 같은 다른 계산을 잘못 연결할 수 있다. 이번 목적에 부적합하다. |
| 미리보기 직전에 임시 지표를 DB에 저장하고 정리 | 현재 Pivot 호출을 거의 그대로 이용 | 취소·실패·경합 때 찌꺼기와 관측 가능한 쓰기가 생긴다. 채택하지 않는다. |

첫 지원 범위는 본인이 소유한 활성 DuckDB 파일 소스와 저장된 `SEGMENT_PIVOT` 및 일반 차트가 함께 있는 최대6블록이다. 명시 제외 후에도 일반 차트가 최소1개 있어야 한다. 일반 다축 Pivot이나 Pivot-only 대시보드 지원으로 확대하지 않는다.

계산은 기존 canonical native 집계와 기존 검증기가 지원하는 FORMULA 의존 그래프만 연결한다. 비율·가중 평균·고유값은 기존 의미 그대로 재집계한다. 중첩 FORMULA 등 기존 연결기가 거절하는 정의는 거절한다. 소스가 바뀌는 불투명 `businessBasis`/차원 업무 기준을 ID만 바꾸어 이식하지 않는다. 첫 단위에서 해당 고정 의미가 필요한 블록은 명시 미지원으로 표시하고 사용자가 제외하거나 중단한다. 업무 의미 이식은 별도 후속이다.

공통 행 AST 조건과 Pivot HAVING 조합은 현재 제한을 유지한다. 수신자·공개 게시본 remix, 현재 파일 교체, 지표 이름 기반 재사용 추정, 조건 단위 변환, 원본 상세 조회, 새 AI 기능은 제외한다. gpt-6-luna 설정과 VoiceOver BLOCKED를 유지한다.

## 3. 현재 코드에서 바꿔야 하는 경계

- `DashboardReuseService.original`은 `studioPivots`가 있으면 차단하며, Studio 블록 수와 일반 widget 수가 같다고 검사한다. 혼합 문서는 저장한 Studio 문서·legacy snapshot·차트 subset·명시 블록 순서가 함께 일치하는지 검증해야 한다. 손상·누락 문서를 차트 전용으로 간주하지 않는다.
- `structured-reuse.ts`는 차트의 고정 metric link와 FORMULA leaf만 계획한다. Pivot의 선택 지표·HAVING 참조까지 같은 그래프에 포함시켜야 한다.
- `BiSegmentService`는 `bi.metrics`와 `bi.prepare(metricId)`로 저장 지표를 다시 읽는다. DB에 없는 후보 지표는 이 공개 경로에 가짜 ID로 주입할 수 없다.
- `StudioPivotService`는 현재 catalog revision·measureRefs·dimensionRefs 및 새 블록의 본인 저장 보기 출처를 검증한다. 이번 확장 때문에 일반 편집기의 이 검사를 완화하지 않는다.
- 복제 미리보기와 저장의 `widgets[index]` 결합은 일반 차트에만 적용된다. Pivot을 일반 Widget으로 만들거나 SQL 위젯으로 위장하지 않는다.

## 4. 고정 복제 계획과 연결 규칙

서버는 원본의 저장 revision, Studio digest, 소스 파일 버전, 사용 지표 ID/정의 버전/정의 digest와 actor·현재 권한 문맥을 읽는다. Pivot의 지표는 현재 활성 canonical 정의가 블록 참조 버전과 일치하는 때만 고정한다. 원본 차트는 기존 저장 snapshot의 정의와 실제 canonical SQL 연결을 검증한다.

계획은 차트/Pivot과 독립된 안정 블록 키, 원본 순서, 모든 폭 배치, 공통 범위, 블록별 Pivot 범위, 선택한 블록 및 지표 의존 그래프를 가진다. 미리보기용 지표 키와 실제 DB ID를 서로 다른 타입으로 취급한다. 서로 다른 원본 정의를 이름만 같다는 이유로 합치지 않는다. 같은 원본 지표 ID·버전·정의 digest만 계획 안에서 중복 제거한다.

필요 열은 선택 블록의 차원 두 축, 지표 leaf의 column/denominatorColumn/weightColumn, 공통 및 Pivot의 필터·날짜 열과 명시 defaultDateColumn에서 구한다. 날짜 열의 명시 null도 보존한다. 제외한 블록만 쓰는 열은 더 이상 필수가 아니다. 숫자/범주/시간의 기존 호환성 및 실제 canonical 컴파일을 모두 통과해야 한다. 같은 이름·호환 타입만 자동 연결하며 다른 이름은 사용자가 선택한다. 같은 Pivot의 두 축이 한 대상 열로 합쳐지는 연결은 거절한다. native 정의를 대상의 최신 업무 유형/기본 날짜로 암묵 재해석하지 않는다.

필터 값·NULL·날짜 경계·UTC·기간 단위·HAVING 비교 연산자/임계값·표시 단위와 정밀도는 보존한다. 환율·문자열 날짜 변환·업무 분류 값 변환을 추정하지 않는다. 통화는 기존 `assertReuseCurrency` 정책과 명시 확인을 유지한다. 공통 필터가 같은 열의 Pivot 필터보다 우선하고 공통 날짜가 Pivot 날짜보다 우선하는 현재 규칙을 그대로 적용한다. 조건을 평탄화해 AND 하거나 조용히 버리지 않는다.

## 5. 쓰기 없는 혼합 미리보기

1. 기존 owner 원본 조회와 대상 source 권한·활성·파일 snapshot 검사를 수행한다.
2. 서버가 연결 표에서 canonical 후보 정의와 FORMULA leaf를 만든다. 원본 검증 실패·매핑 누락·지원 밖 의미는 계산 전에 오류로 반환한다.
3. 일반 차트는 기존 미리보기 컴파일 경로를 이용한다. Pivot은 저장 지표 준비와 SQL 실행을 분리한 공통 집계 핵심을 이용한다.
4. 공통 집계 핵심은 서버가 준비한 표현식·바인딩·출력 정의만 받는다. 외부 요청의 expression/SQL/catalog/가짜 metric ID를 받는 필드를 만들지 않는다. 공개 `segments`/details/export의 strict 입력 검증과 저장 지표 권한 검사는 유지한다.
5. 후보 Pivot도 공통 source filter/date → 전체 그룹 HAVING → 기여 행 재집계 → 행·열·전체 합계 순서를 따른다. 평균/비율을 그룹 값의 단순 합이나 평균으로 바꾸지 않는다. 기존 그룹·열·추세 한도와 잘림 표시를 유지한다. 복제 응답에 원본 행은 포함하지 않는다.
6. SQL 전후에 현재 actor/권한·원본 revision/digest·참조 지표·대상 파일/기준을 재검사한다. 후보 그래프는 고정 plan digest와 비교하며 DB 지표 재조회로 후보가 사라졌다고 판정하지 않는다. 원본 지표 검사는 별도로 유지한다.
7. 전부 성공했을 때만 기존 5분/최대100개/계획당128KiB ticket을 발급한다. 실패한 부분 결과를 저장 가능한 미리보기로 반환하지 않는다.

SQL 실행은 metadata 쓰기 lease/transaction 밖이다. 공통 집계 핵심 분리는 기존 저장 지표 호출과 후보 호출의 계산을 공유하기 위한 것이며, 새로운 SQL 생성 엔진을 병렬로 만들지 않는다.

## 6. 원자 저장과 출처

저장 입력은 기존처럼 ticket/requestId만 받는다. title/열 연결/블록 선택이 바뀌면 기존 ticket을 폐기하고 전체 미리보기를 다시 요구한다. ticket은 첫 requestId에 묶이며 동일 요청의 결과 유실은 기존 영수증으로 확인한다.

기존 metadata 조정·원자 transaction 안에서 현재 계정/epoch·소유/접근·소스 활성·원본 revision/문서 digest·참조 지표 버전·대상 파일 및 정책 기준을 재검사한다. 대상의 지표 추가 전 catalog 기준도 고정 계획과 일치해야 한다. 기존 Source→Metric 잠금 helper와 Dashboard 부모 조정 경로를 재사용하고, 두 소스의 획득 순서를 일정하게 한다. 구현 전 관련 저장 writer의 실제 잠금 순서를 대조해 역순을 만들지 않는다. 이 선택 경로의 검증을 모든 writer의 운영 경합 통과라고 보고하지 않는다.

leaf부터 새 Metric을 저장한 후 FORMULA, 차트 링크, Pivot 선택 지표/HAVING 참조를 새 ID로 치환한다. 저장하는 새 지표 수는 계획의 고유 노드 수이며 대상 기존 지표를 수정하거나 이름으로 중복 판정하지 않는다. 긴 SQL을 이 transaction에서 다시 실행하지 않는다. 서버 검증 계획과 저장할 정의의 정규화 digest가 다르면 rollback한다.

새 지표가 포함된 최종 target catalog로 모든 복사 Pivot의 recipe revision을 만든다. 이때 현재 transaction의 manager로 catalog를 읽어 미커밋 지표를 누락하거나 다른 연결로 metadata lease에 재진입하지 않는다. 기존 대상의 다른 저장 보기 revision은 새 지표 추가로 무효화될 수 있으며 현재 catalog 전체 revision 정책을 바꾸지 않는다. 화면은 새 지표가 생성된다는 점을 저장 전에 알린다.

`studioPivots`, `studioLayouts`, `studioBlockOrder`, 일반 차트 items 및 StudioState를 한 transaction으로 저장한다. 안정 키→최종 block ID 대응으로 결합하며 차트 index로 Pivot을 대입하지 않는다. 마지막 Dashboard revision으로 StudioState.legacyRevision과 영수증을 맞춘다. 어느 단계든 실패하면 지표·대시보드·Widget·StudioState·영수증 모두 rollback한다.

복제의 Pivot 출처는 권한 검증한 원본 저장 문서 + 고정 지표 그래프 + 전체 미리보기 ticket이다. 사용자의 PersonalView를 암묵 생성하지 않는다. 이 서버 전용 저장 경로는 검증한 복제 계획만 저장하며 일반 편집기의 `assertSaved`와 외부 문서 검증은 그대로 유지한다. 저장 후에는 새 문서의 기존 블록으로 정상 재조회·편집할 수 있어야 한다.

영수증 재조회도 현재 복사본 접근과 actor/epoch를 확인하며 과거 영수증을 현재 권한 증명으로 사용하지 않는다. 서버 재시작으로 ticket이 없어지고 영수증도 없으면 초안 입력을 보존해 재미리보기를 안내한다. 이미 저장된 요청은 새 자원을 만들지 않고 기존 비공개 사본으로 연결한다.

## 7. API·화면 호환과 디자인

기존 차트 전용 응답과 요청은 유지한다. 소유자 draft의 블록 설명에 kind와 사용 열/지표·조건 요약을 추가한다. 혼합 미리보기는 구분 가능한 버전/종류의 payload와 blockId 기반 결과 목록을 반환하고, 차트 snapshot 필드에 Pivot을 끼워 넣지 않는다. 응답 검사기는 모르는 종류나 누락 블록을 오류로 처리한다. share/publication origin의 Pivot 차단은 유지한다.

Studio의 저장본 복제 진입점을 Pivot 혼합 문서에도 제공한다. 현재 초안에 Pivot이 생겼다는 이유만으로 저장본의 지원 여부를 추정하지 않으며, 원본 마지막 저장본을 사용한다는 설명을 유지한다. 기존 같은 소스 빠른 복제도 보존한다.

기존 shadcn UI와 source/column mapping 단계를 재사용한다. 각 블록에서 사용 열과 지표/조건을 접어서 확인할 수 있고, 미지원 블록은 이유와 명시 제외를 제공한다. 제외 후 일반 차트가0개이면 미리보기/저장을 차단한다. 미지원 블록을 기본 해제하거나 자동 제외하지 않는다.

소스/열/제목/선택 변경은 기존 abort+sequence로 묵은 응답과 미리보기/ticket을 무효화한다. 저장 결과 불명확 시 동일 requestId와 입력을 보존하고 추가 저장을 막는다. 오류·재시도·성공은 접근 가능한 상태 안내로 제공한다. 결과는 원본과 새 비공개 Studio 링크를 구별해 보여준다.

대표 화면은390/768/1440px다. 기존 일반 버튼/입력36px·도구32px 토큰을 따르고 모바일 입력은16px를 유지한다. 긴 열 이름과 지표명을 줄바꿈해 연결 관계를 읽을 수 있게 하고, 전체 페이지 가로 넘침을 허용하지 않는다. Pivot의 넓은 표만 명시적인 내부 가로 스크롤을 사용한다. 로딩에도 영역과 포커스를 보존하며 Tab/Shift+Tab/Enter/Space/Escape 및 표의 기존 키보드 조작을 확인한다.

SPR-01/02의 원본 및 변형 데이터는 공개 샘플만 사용한다. 중복 행 때문에 distinct 지표가2배가 된다고 가정하지 않는다. 위2배 정답은 매출/이익의 SUM 및 이들의 비율에 한정한다. 고정 임계값으로 고객 자격을 다시 판정해야 하며 일반 데이터에서2배 합계를 가정하지 않는다. 설계 점검에서 이 CSV의 Decimal 독립 계산으로18/36행 모두 자격2그룹·기여8/16행과 위 정답을 확인했다. 이는 제품 미리보기 실행 PASS가 아니다. 원본 Rill 계산/화면 증빙을 재사용하고 새 변형을 Rill에서도 실행하지 않았다면 새 데이터의 Rill 동등성 PASS를 선언하지 않는다.

단위 검증은 순수 그래프/매핑/ID 결합과 집계 핵심 분리의 의미 보존을 우선한다. 통합 검증은 실제 임시 DuckDB+SQLite로 preview 쓰기0, 저장/rollback/영수증을 확인한다. 권한·동일 부모 잠금을 바꾸면 격리 MySQL 경합을 별도로 실행해야 하며 미실행이면 NOT_RUN으로 남긴다. FE에서는 혼합 payload 검사·묵은 응답·ticket 무효화·실패 보존을 선택 검증한다. 변경 범위 type/lint/build와 실제 Ego 화면을 확인한다. 전체 기존 E2E를 작업마다 반복하지 않는다.

증빙은 저장소 밖 전용 실행 폴더에 커밋/diff·데이터 변형 방식·독립 정답·실제 요청/지속 상태·케이스 상태와 대표 캡처를 남긴다. 사용자에게 실제 캡처를 보여준다. API 준비를 UI 조작 통과라고 표시하지 않고 기능/숫자와 디자인 PASS를 구별한다. 계정 비밀번호·토큰·고객 자료는 기록/커밋하지 않는다.

## 9. 종료와 별도 잔여 조건

이 단위의 종료 조건은 지원 범위의 SPR-01~07 실행 결과·남은 차단을 명시하고, 오류 수정 후 해당 조건을 재검증하는 것이다. 통과한 조건은 관련 변경 없으면 반복하지 않는다. 실제 휴대폰/멀티터치·VoiceOver·운영 부하·모든 MySQL writer 경합·수신자 remix·업무 의미 이식·일반 Pivot 전체·제품 전체 P5/TC005 및 기업16개 요건 수용은 이 설계의 완료로 승격하지 않는다.

문서 자체 점검: 미결 선택지·임시 지표 선저장·공개 catalog override·자동 PersonalView 생성은 없다. 신규 DB 스키마/의존성은 필요하지 않다. 구현 계획과 코드 작성은 이 설계의 검토 승인 후 진행한다.
